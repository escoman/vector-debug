# Known Issue — VRAM Planes: ложное «чтение» и «вечная» подсветка в Live-режиме

- **Статус:** дефекты 1–4 в окне **исправлены** (2026-10-29, см. «Что
  исправлено»). Открытыми остаются первопричина части симптомов — классификация
  fetch в `src/backend.cpp:799–846` — и попутно найденный дефект
  «наблюдательских» чтений через `DebugBackend::readMemory()`.
- **Обнаружено:** при разборе бенчмарка `roms/tests/spr-speed` (Vector-06C) на
  сборке `v06c-mcp 0.6.7`, gitHash `7de7d7f`
- **Влияние (до исправления):** окно VRAM Planes в Live-режиме систематически
  завышало «чтения» (показывало read+write там, где идёт только запись) и не
  гасло при паузе. Две карты памяти на одних и тех же данных давали разные
  картины, потому что брали активность из разных источников.

## Что исправлено (2026-10-29)

Источником активности для окна стала посекундная статистика `MemoryStats`, а не
кольцевой буфер событий `memoryHistorySnapshot()`:

- `src/events.h` — в `MemoryStats` добавлены `lastDataReadTime` (только чтения
  данных) и `lastFetchTime` (выборки кода). `lastReadTime` по-прежнему означает
  «любое чтение, включая fetch» и не менялся ради Memory Map.
- `src/idebug_backend.h` — новый метод `byteActivitySnapshot(uint16_t start,
  size_t size)` со структурой `ByteActivityState { lastDataRead, lastWrite,
  lastFetch }`. Реализация по умолчанию возвращает пустой вектор, поэтому моки
  в тестах править не пришлось.
- `src/backend.cpp` — реализация метода (копия диапазона `memStats`, с
  ограничением на границе `0x10000`), разделение метки времени в
  `onMemoryRead()` по признаку `isFetch`, обнуление новых полей в `clearStats()`.
- `src/backend.cpp`, `loadRom()` — теперь вызывает `clearStats()`: статистика
  принадлежит той машине, которая её произвела, и новый ROM не должен
  наследовать активность предыдущей программы.
- `gui/plane_screen_window.cpp` — кольцевой буфер больше не читается; окно берёт
  `byteActivitySnapshot(base, 8192)` раз в кадр. `Fetch` не считается чтением
  данных: он рисуется синим и только при включённом чекбоксе **Fetch** (по
  умолчанию выключен, недоступен при снятом **Live**). Кэш `accessTimes_`
  удалён целиком, вместе с ним ушли дефекты 3 и 4.

`tests/test_backend.cpp`: добавлен `test_byte_activity_snapshot()` — проверяет,
что чтение данных (`MOV A,M`), запись (`STA`) и выборка кода (операнды `MVI`)
попадают в разные поля, что `reset()` их обнуляет и что запрос за границей
`0xFFFF` не выходит за массив. Набор `test_backend`: 124/124.

### Изменение поведения, о котором стоит знать

Галочка **Live** больше ничего не очищает при включении: раньше off→on
показывало карту, которая сразу же заново заполнялась всей глубиной кольца (до
50 000 событий), теперь показывается не более последних 500 мс честной
активности — потому что источник стал wall-clock, а не кэш окна.

### Ловушка сентинеля времени (нашлась при первом запуске правки)

Первая версия правки покрасила **все** байты плоскости как «прочитанные»: в
`MemoryStats` «обращений никогда не было» — это `TimePoint::min()`, а проверка
активности была скопирована со старого кода и сравнивала с `time_point()`
(эпохой). `now - TimePoint::min()` переполняет int64 наносекунд и уходит в
минус, а отрицательная длительность меньше 500 мс, то есть любой нетронутый
байт выглядел «только что прочитанным». В старом коде этого не было видно:
окно всегда писало `now`, и сентинель в него не попадал.

Сравнение вынесено в `IDebugBackend::byteActivityRecent()` — она отбрасывает
сентинель до вычитания, и ею должны пользоваться все потребители
`ByteActivityState`. Покрыто четырьмя проверками в
`test_byte_activity_snapshot()` (min/эпоха — неактивны, только что — активен,
1 с назад — неактивен).

## Симптом

ROM `roms/tests/spr-speed` рисует пять спрайтов в одну и ту же колонку `x = 0`
(сцены OLD / NEW / MASK / SMC / STUB, `y = 8 / 56 / 104 / 152 / 200`), то есть
все они пишут в колонки 0–2 плоскостей П1 (`0xC000`) и П0 (`0xE000`). Маска
(`MASK ENGINE`) — единственный код в ROM, который читает VRAM.

Наблюдаемая картина:

| Где смотрим | Что видно | На самом деле |
|---|---|---|
| Memory Map, блоки `0xC000–0xC2FF`, `0xE000–0xE2FF` | жёлтые кубики (read+write) | корректно: блок = 256 Б = одна колонка страницы, чтения маски попадают в те же блоки |
| Memory Map, фон шахматки под MASK | красный (только запись) | корректно: `fill_checker` пишет 32 строки, маска читает только свои `LEN` (26–28 / 6–8) |
| **VRAM Planes (Live), П1/П0** | зелёные/жёлтые байты в колонках 0–2, в том числе там, куда пишут NEW/SMC/STUB | **баг**: см. дефекты 1–2 |
| **VRAM Planes (Live) при остановленном эмуляторе** | подсветка не гаснет | **баг**: см. дефект 2 |

## Дефект 1 — `Fetch` приравнен к `Read` — исправлено в окне

`gui/plane_screen_window.cpp:62–76`:

```cpp
if (liveMode_) {
    auto events = backend.memoryHistorySnapshot();
    auto now = std::chrono::steady_clock::now();
    for (const auto &evt : events) {
        uint16_t addr = evt.virt;
        if (addr >= base && addr < base + 8192) {
            auto &times = accessTimes_[addr];
            if (evt.type == MemoryAccessType::Read || evt.type == MemoryAccessType::Fetch) {
                times.lastRead = now;      // fetch тоже «чтение»
            } else if (evt.type == MemoryAccessType::Write) {
                times.lastWrite = now;
            }
        }
    }
}
```

Классификация read/fetch в free run делается эвристикой «чтение с адресом
`virt`, где `virt + 1 == PC`, — это фетч следующей инструкции»
(`src/backend.cpp:799–846`, там же пометка `Known limitation`). Эвристика
ошибается, и это видно по счётчикам. После `debug_clear_memory_access_map` и
прогона ~0.6 с:

| блок | read_count | write_count | fetch_count | execute_activity (`debug_get_memory_map`) |
|---|---|---|---|---|
| `0xC000` | 4568 | 15128 | **6432** | **0** |
| `0xC100` | 4584 | 15194 | **6432** | **0** |
| `0xC200` | 1951 | 10241 | **6432** | **0** |
| `0xE000` | 4568 | 15128 | **6432** | **0** |
| `0xE100` | 4584 | 15194 | **6432** | **0** |
| `0xE200` | 1951 | 10234 | **6432** | **0** |

Три независимых признака того, что счётчик `fetch` в этих блоках не отражает
исполнение кода:

1. `execute_activity = 0` во всей VRAM (`0x8000–0xFFFF`) в кумулятивной карте
   `debug_get_memory_map`, хотя `execute_activity` считается по тому же массиву
   `executeCount_`, который инкрементирует детектор начала инструкции.
2. Значение `fetch_count` **одинаково во всех шести блоках** (в другом прогоне —
   `8672` в каждом). Для адресного учёта (`block = addr >> 8`) это невозможно:
   шесть разных блоков не могут независимо набрать одно и то же число.
3. Брейкпоинты внутри VRAM (`0xC093`, `0xC0A3`, `0xC0C7`) не срабатывают за
   многосекундные прогоны — код там не исполняется.

Итог: адреса событий настоящие (это реальные обращения по этим адресам), но
**тип** выставлен неверно. Именно из-за строки `|| MemoryAccessType::Fetch` любой
такой ложный fetch окрашивал байт плоскости как «чтение».

**Как исправлено:** строка `|| Fetch` удалена вместе с кольцевым буфером; окно
теперь берёт раздельные метки `lastDataReadTime` / `lastFetchTime`, поэтому
ложный fetch больше не окрашивает байт как чтение данных (он виден только в
опциональном синем слое). Сама эвристика в `src/backend.cpp` **не тронута** —
см. «Остаётся открытым».

## Дефект 2 — у событий нет собственного времени, окно штампует `now` — исправлено

`src/events.h:43–53` — в `MemoryAccessEvent` нет метки времени:

```cpp
struct MemoryAccessEvent
{
    uint64_t instructionSequence;
    MemoryAccessType type;
    uint16_t virt;
    uint32_t phys;
    uint8_t value;
    bool stack;
};
```

Поэтому окно ставит `times.lastRead/lastWrite = now` (**время перерисовки**) для
каждого события, которое ещё лежит в кольцевом буфере. Последствия:

1. **При паузе подсветка не гаснет никогда.** `buildPlanePixels()` вызывается на
   каждом кадре GUI (`gui/plane_screen_window.cpp:388–392`), кольцо не
   очищается при остановке, события в нём не стареют — значит каждые 16 мс они
   заново помечаются как «только что». Проверка `isActive()` с
   `ACTIVITY_DURATION = 500 ms` (`gui/plane_screen_window.h:52`) в этом режиме
   не работает вовсе.
2. **`ACTIVITY_DURATION` в этом окне фактически не реализован.** Реальное окно
   наблюдения = глубина кольца `DEFAULT_MEMORY_HISTORY = 50000` событий
   (`src/backend.cpp:24`, push в `:834`). В free run это единицы–десятки
   миллисекунд эмуляции, а не 500 мс. Окно показывает «попал ли адрес в
   последние 50 000 событий», а не «обращались ли к нему за 500 мс».
3. **Расхождение с Memory Map.** Memory Map берёт активность из
   `liveActivitySnapshot()` (`src/backend.cpp:1737–1762`), то есть из
   wall-clock меток `MemoryStats::lastReadTime/lastWriteTime`
   (`src/events.h:81–95`), и корректно гаснет через 500 мс даже при остановленном
   CPU. VRAM Planes берёт другой источник и ведёт себя иначе — два окна
   противоречили друг другу на одних данных.

**Как исправлено:** окно перешло на тот же wall-clock источник, что и Memory Map
(`memStats` через `byteActivitySnapshot()`), с разделением чтения данных и fetch.
Проверка `isActive()` с `ACTIVITY_DURATION = 500 ms` теперь работает и при
остановленном CPU. Кольцо для окна не читается вовсе, поэтому «окно наблюдения
= глубина кольца» больше не при чём.

## Дефект 3 — `accessTimes_` сбрасывается только при выключении Live — исправлено

`gui/plane_screen_window.cpp:278–283` очищает карту лишь при снятии галочки
`Live`. При `Reset`, загрузке нового ROM, `clearHistory()` /
`debug_clear_memory_access_map` накопленные метки остаются, и после возобновления
работы первые кадры показывают активность, которой уже нет.

**Как исправлено:** кэш `accessTimes_` удалён, сбрасывать больше нечего — окно
читает состояние напрямую из бэкенда. Дополнительно `loadRom()` теперь вызывает
`clearStats()`, так что загрузка нового ROM не наследует статистику предыдущего
(`reset()`/`restart()` чистили статистику и раньше).

## Дефект 4 — полное копирование кольца на каждый кадр GUI — исправлено

`memoryHistorySnapshot()` (`src/backend.cpp:987–990`) возвращает копию всего
кольца (`vector<MemoryAccessEvent>`, до 50 000 элементов) и вызывается 60 раз в
секунду, хотя нужны только 8192 адреса текущей плоскости. Это постоянные
мегабайты копирований в секунду и лишняя нагрузка на mutex эмуляционного потока.

**Как исправлено:** вместо копии кольца на каждый кадр — копия 8192 записей
`ByteActivityState` (три `time_point` на байт) для запрошенного диапазона.
Кольцо осталось только для журнала обращений (`debug_get_memory_access_log`).

## Остаётся открытым — «наблюдательские» чтения

При проверке обнаружилось, что в потоке обращений есть события, которых не
порождает эмулируемая программа. `DebugBackend::readMemory()`
(`src/backend.cpp:372–375`) вызывает `target_->readMemory()`, а тот идёт через
`Memory::read`, то есть **срабатывают `onread`-колбэки** и в кольцо/статистику
попадает полноценный `Read`. Этим путём пользуются `debug_get_state`,
дизассемблер, инспектор памяти, окна брейкпоинтов/xrefs/memory access и несколько
путей `AgentApi` — то есть опрос GUI и MCP сам себя инструментирует.

Доказательство (брейкпоинты `0x0F77` и `0x0F78`, маска в `por_run`):

```text
fetch 0x0F76
read  0x17B4
read  0x0F77  0xA6    <- фетч опкода ANA M (валидно)
fetch 0x0F77
read  0xC093  0xFF    <- чтение данных маской: классифицировано верно
read  0x0F78  0xEB    <- байт следующей инструкции, прочитанный наблюдателем
```

Последняя строка — не исполнение: GUI/MCP прочитал `0x0F78` через
`readMemory()`, и событие попало в счётчики. Помимо ложных `Read`, такой опрос
может сдвигать `fetchRemaining_` (окно фетча опкода), то есть влиять на
классификацию соседних событий.

Исправление не сделано, нужна отдельная задача: читать через `readMemoryRaw()` /
`peekMemory()` (без колбэков) либо ввести на время наблюдения отдельный флаг
«не инструментировать». Мутировать `Memory::onread` при работающем CPU-потоке
нельзя — это уже приводило к SIGSEGV в MCP-сервере.

## Остаётся открытым — первопричина в `src/backend.cpp`

Ложная классификация fetch в free run (`src/backend.cpp:799–846`):
`fetch_count ≠ 0` в блоках с `execute_activity = 0` и **одинаковые** значения в
шести независимых блоках — признак того, что окно фетча «перетекает» через
границу инструкции. Воспроизводится на перепроверке 2026-10-29 (7264 в каждом
из шести блоков, см. «Приложение», опыт E).

Замечание к диагностике: `executeCount_` в кумулятивной карте не очищается
вместе со `runtimeAccessMap_` при `debug_clear_memory_access_map`, поэтому
сравнивать `fetch_count` с `execute_activity` после очистки карты нельзя —
`execute_activity` может быть меньше `fetch_count` просто из-за разного момента
обнуления.

## Статус пунктов исходного плана

1. **Не считать `Fetch` чтением данных** — сделано, включая чекбокс «Fetch»
   (синий слой), по умолчанию выключенный.
2. **Отказаться от кольца в пользу посекундной статистики** — сделано по
   варианту с `MemoryStats` (`lastDataReadTime`/`lastFetchTime`), но через новый
   узкий метод `byteActivitySnapshot()`, а не через полный
   `memoryStatsSnapshot()` (тот копирует 65536 записей на кадр). Вариант с меткой
   времени в `MemoryAccessEvent` не понадобился.
3. **Сбрасывать `accessTimes_`** по `Reset`, `LoadRom`, `clearHistory()` —
   сделано иначе: кэша больше нет, а `loadRom()` чистит `memStats`.
4. **Первопричина fetch в free run** — не сделано, вынесено в отдельную задачу
   (см. выше).

## Критерии приёмки

- [x] При остановленном эмуляторе подсветка гаснет за ~500 мс — выполнено:
  источник стал wall-clock, `isActive()` теперь реально работает при паузе.
- [x] На `spr-speed` в П1/П0 зелёный появляется только на байтах `LEN` маски
  (адреса, которые читает `ANA M` в `por_run`, `0x0F77`); байты, куда пишут
  NEW/SMC/STUB вне силуэта маски, — только красные. Выполнено в той части,
  которая зависела от окна: чтение данных и fetch разведены, `Fetch` по
  умолчанию не рисуется (проверено, что `ANA M` по `0xC093` классифицируется как
  `read`). Остаточный риск — «наблюдательские» чтения (раздел выше): они дают
  настоящий `Read` по адресу, который программа не читала.
- [ ] Множество «прочитанных» байт в окне совпадает с `read_count` из
  `debug_get_memory_access_map`. **Не проверено**: счётчики в карте кумулятивные
  и поблочные, окно показывает 8192 Б плоскости по меткам времени; оба источника
  при этом содержат одни и те же наблюдательские чтения, так что совпадение
  возможно, но завышено одинаково.
- [x] Пауза/резюм не оставляют «залипших» байт — выполнено. Формулировка «Live
  off→on полностью очищает подсветку» **изменена осознанно**: окно больше ничего
  не кэширует, поэтому при включении Live показывается не более последних 500 мс
  актуальной активности, а не карта, которая через кадр заполнялась заново всей
  глубиной кольца.

## Приложение: как проверялось

```text
ROM:        roms/tests/spr-speed (10635 байт), 5 сцен, все в x=0
Инструмент: v06c-mcp 0.6.7, gitHash 7de7d7f, build 2026-10-27

Опыт A (маска — единственный читатель VRAM):
  breakpoint 0x0F77 (ANA M внутри por_run)  ->  сработал, HL = 0xC093
  debug_get_memory_access_log (после step)  ->  {0x0F77 fetch 0xA6}, {0xC093 read 0xFF}

Опыт B (кумулятивная карта):
  debug_get_memory_map:
    read_activity = 1 ровно у 0xC000, 0xC100, 0xC200, 0xE000, 0xE100, 0xE200;
    у остальных блоков VRAM read_activity = 0;
    execute_activity = 0 во всей VRAM

Опыт C (окно кольца):
  debug_clear_memory_access_map; run ~0.6 s; pause
  debug_get_memory_access_map: см. таблицу в дефекте 1
  (в другом прогоне fetch_count = 8672 в каждом из тех же шести блоков)

Опыт D (код в VRAM не исполняется):
  breakpoints 0xC093, 0xC0A3, 0xC0C7 — ни одного срабатывания за несколько секунд

Опыт E (перепроверка 2026-10-29, та же сборка 0.6.7 / 7de7d7f):
  debug_clear_memory_access_map; run 1 s; pause
  debug_get_memory_access_map:
    0xC000/0xC100/0xC200/0xE000/0xE100/0xE200 -> fetch_count = 7264 в каждом
    (дефект воспроизводится; окно его больше не показывает как чтение)
  debug_get_memory_map: execute_activity = 0 во всех шести блоках

Опыт F (наблюдательские чтения):
  breakpoints 0x0F77 + 0x0F78; clear map; run -> pause на 0x0F77,
  run -> pause на 0x0F78; debug_get_memory_access_log (хвост):
    fetch 0x0F76, read 0x17B4, read 0x0F77 (0xA6), fetch 0x0F77,
    read 0xC093 (0xFF), read 0x0F78 (0xEB)   <- последняя строка от наблюдателя
```

Проверка «где именно читается VRAM» по исходникам ROM: во всём `spr_smc.asm`
только две читающие инструкции — `ANA M` (`0x0F77`) и `ORA M` (`0x0F79`), причём
`ORA M` после `XCHG` читает таблицу цвета в ROM; `MOV M,A`, `MVI M,0`, `STAX D`
(в `plane_blit`, в копирующей «лесенке» `0x7000`, в `erase_plane`,
`fill_checker`) — только запись.
