# Stage 6.9 — MCP-First ROM Analysis

## Цель

Закрепить за MCP Debugger статус **единственного источника фактических данных** при анализе ROM.

AI-агент (Qwen/Qoder) **не является дизассемблером Vector-06C**. Он является аналитиком, использующим Debugger как источник фактов.

Целевая схема:

```text
ROM
 ↓
MCP Debugger
 ↓
DebugAdapter
 ↓
Agent API
 ↓
disassembly / CPU / memory / I/O / trace
 ↓
Qwen analysis
```

Запрещённая схема:

```text
ROM
 ↓
Qwen
 ↓
самостоятельный disassembler
```

---

# 1. Обязательное правило MCP-first

При анализе Vector-06C ROM **MCP Debugger является основным инструментом анализа**.

Агент не должен самостоятельно:

- читать ROM как набор байтов и самостоятельно дизассемблировать его;
- вычислять инструкции по opcode;
- вручную строить control flow вместо использования MCP;
- самостоятельно интерпретировать hex-дамп как программу;
- заменять результаты MCP собственным дизассемблированием.

---

# 2. Подключение MCP перед анализом

Перед анализом ROM необходимо убедиться, что MCP Debugger доступен.

Если MCP-сервер ещё не запущен — **запустить MCP-сервер предусмотренным проектом способом**.

Агент не должен переходить к самостоятельному дизассемблированию только потому, что MCP ещё не был запущен.

При невозможности запуска MCP необходимо явно сообщить:

```text
MCP Debugger недоступен, поэтому достоверный ROM-анализ выполнить невозможно.
```

Не заменять MCP-анализ самостоятельным декодированием ROM.

---

# 3. Загрузка ROM через MCP

ROM загружается через:

```text
debug_load_rom
```

После загрузки проверить состояние через:

```text
debug_get_state
```

и получить необходимые данные средствами MCP.

---

# 4. Дизассемблирование только через MCP

Для получения инструкций используется:

```text
debug_disassemble
```

Результат MCP является **источником фактического дизассемблирования**.

Агент анализирует:

- address
- opcode/instruction
- operands
- control flow

— полученные от Debugger.

Не следует повторно декодировать opcode самостоятельно.

---

# 5. Понимание поведения через выполнение

Статического дизассемблирования недостаточно для вопросов фактического поведения ROM.

Использовать соответствующие MCP tools:

```text
debug_get_cpu_state
debug_get_instruction_history
debug_get_execution_trace
debug_get_io_trace
debug_read_memory
debug_get_memory_map
debug_get_vram_info
debug_get_screen_info
```

При необходимости использовать:

```text
debug_run
debug_pause
debug_step
```

Важно: `run` / `pause` являются запросами изменения состояния. После них необходимо запросить фактическое состояние Debugger, а не предполагать, что операция уже завершена.

---

# 6. Не анализировать ROM по одному только hex dump

Если MCP вернул `address → byte`, этого недостаточно для утверждения:

- это инструкция
- это таблица
- это данные
- это обработчик
- это код

Сначала получить `debug_disassemble`, затем подтвердить назначение участка через:

- execution trace
- instruction history
- memory access
- I/O trace
- call graph
- xrefs

---

# 7. Разделение ответственности

### MCP Debugger

Получает объективные данные:

- ROM contents
- disassembly
- CPU state
- memory
- I/O
- execution
- traces
- symbols
- functions
- xrefs
- call graph
- VRAM
- screen state

### AI-агент (Qwen)

Выполняет:

- interpretation
- correlation
- hypothesis generation
- reasoning
- classification
- report generation

Принцип:

```text
MCP → Facts
Qwen → Analysis
```

---

# 8. Приоритет MCP над собственными вычислениями

Если агент может получить информацию через MCP, необходимо использовать MCP.

Например, вместо:

```text
Я сам вычислю, что opcode C3 означает JMP.
```

необходимо получить дизассемблирование через `debug_disassemble` и использовать его результат.

То же относится к:

- длине инструкции
- операндам
- адресам переходов
- CALL/RET
- RST
- обращениям к памяти
- I/O
- состоянию CPU
- execution trace

---

# 9. Самостоятельные вычисления — только как проверка

Агент может самостоятельно рассуждать над уже полученными MCP-данными.

Например:

```text
MCP: 0142: DCX B
Агент: инструкция изменяет пару BC.
```

Но агент не должен сначала брать байты ROM и самостоятельно определять:

```text
0142 = DCX B
```

если эта информация может быть получена через MCP.

Самостоятельные вычисления используются для:

- проверки
- сопоставления
- логического вывода

а не для замены Debugger.

---

# 10. Обязательный порядок анализа ROM

Для обычного запроса «Проанализируй <rom>. Что он делает?»:

```text
 1. Найти ROM
 2. Запустить/подключить MCP Debugger
 3. debug_load_rom
 4. debug_get_state
 5. Получить disassembly через debug_disassemble
 6. Определить entry points и control flow
 7. Получить CPU state
 8. При необходимости выполнить ROM
 9. Получить execution history / trace
10. Получить I/O trace
11. Проверить memory / VRAM / screen
12. Сопоставить наблюдения с Knowledge Base
13. Сформировать Facts
14. Сформировать Inferences
15. Сформировать Hypotheses
16. Проверить существенные Hypotheses дополнительными MCP-запросами
17. Сформировать итоговый отчёт
```

Не пропускать шаги 2–5 и не заменять их самостоятельным анализом бинарника.

---

# 11. Если MCP и статический анализ расходятся

Приоритет имеет фактический результат Debugger.

Если собственное рассуждение агента противоречит результату `debug_disassemble`, `debug_get_execution_trace`, `debug_get_io_trace`:

1. считать MCP результат первичным evidence;
2. проверить запрос MCP;
3. при необходимости выполнить дополнительный MCP-запрос;
4. не выдавать собственную интерпретацию за факт.

---

# 12. Запрещённый fallback

Нельзя использовать такой fallback:

```text
MCP недоступен
    ↓
возьму hex dump
    ↓
сам дизассемблирую ROM
    ↓
проанализирую
```

Правильное поведение:

```text
MCP недоступен
    ↓
сообщить об отсутствии Debugger evidence
    ↓
не выдавать предположительный ROM-анализ за достоверный
```

# 15. Критерий проверки Skill

При запросе:

```text
Проанализируй clrs.rom. Что он делает?
```

Агент должен:

- запустить/использовать MCP Debugger;
- загрузить ROM через `debug_load_rom`;
- получить дизассемблирование через `debug_disassemble`;
- использовать MCP для получения runtime evidence;
- не выполнять самостоятельное дизассемблирование ROM;
- не заменять MCP собственным декодированием opcode;
- использовать Qwen только для анализа и интерпретации полученных данных.

Ключевой принцип:

> **Qwen не является дизассемблером Vector-06C. Qwen является аналитиком, использующим Debugger как источник фактических данных.**
