# Known Issue — ASM Exporter: побайтовая потеря на неприсвоенных 8080-опкодах (семейство `NOP`)

- **Статус:** Resolved (исправлено: экспортёр сохраняет байт как `defb`,
  см. раздел «Resolution» ниже)
- **Обнаружено:** Stage 1 ROM-анализ `basic.r0m` (BASIC 2.997, репозиторий
  `vector-games`, `roms/redesign/basic/`) — вердикт `roundtrip_verify: MISMATCH`
- **Влияние:** экспорт **молча** подменял байт образа: любой opcode, который
  дизассемблер описывает как `"NOP"`, печатался мнемоникой `nop` и
  пересобирался в `00h`. Терялось 7 из 256 опкодов i8080.
- **Приоритет:** высокий — ломал сквозной контракт «round-trip байт-в-байт»
  для любого ROM с нелегальными 8080-опкодами; все линтеры при этом green.

Первоисточник отчёта — `vector-games/roms/redesign/basic/reports/`
(там же остался оригинал со ссылкой на эту копию). Ссылки на `src/…`,
`export/…`, `agent/…`, `tests/…` — из `vector-debug`.

## Симптом

`basic.r0m` (17152 байта, SHA-256 `6c632f67718a31f0…`) — распакованный RAM-образ
интерпретатора, база `0x0000`. Прогон пайплайна (`vector-games`):

```bash
utils/analyze/run_pipeline.sh basic --from export_asm
```

```
export_asm            PARTIAL  — экспортёр rc=0, файлов 5, сборка rc=0, 17152 байт
toolchain_lint        PARTIAL  — clean
symbolic_operand_lint PARTIAL  — clean: все адресные операнды именованные
syntax_check          PARTIAL  — clean: собралось без единой претензии
roundtrip_verify      FAILED   — 3 байт(а) различается в 3 диапазоне(ах)
```

`roundtrip_verify.json` → `diff.ranges`:

| адрес | в образе | в пересборке | примечание |
|---|---|---|---|
| `0x0AA7` | `28h` | `00h` | сразу после `RST 08` (`0x0AA6`) |
| `0x0AE9` | `28h` | `00h` | сразу после `RST 08` (`0x0AE8`) |
| `0x1CB5` | `28h` | `00h` | сразу после `RST 08` (`0x1CB4`) |

Ни `toolchain_lint`, ни `syntax_check` не сигнализируют: `nop` — корректная
команда z80asm, она просто собирает не тот байт. Поймать способен только
побайтовый diff.

## Корень (подтверждено кодом)

1. **Дизассемблер помечает неприсвоенные опкоды i8080 как `NOP`.**
   `src/disassembler.cpp:42` (`optable[256]`): позиции `[+0]` первых четырёх
   строк (row `0x0_`, `0x1_`, `0x2_`, `0x3_`) и подстроки `/* 08 */`, `/* 18 */`,
   `/* 28 */`, `/* 38 */` — всюду `{ "NOP", F_IMP }`. Длина — 1
   (`src/opcode_info.h`, `opcode_length[]`, комментарий «NOP (undocumented)»).
   Итого под `NOP` попадают **8 опкодов**:

   ```
   00h (настоящий NOP), 08h, 10h, 18h, 20h, 28h, 30h, 38h
   ```

   Семёмеро из них — unassigned по спецификации Intel 8080 (на i8080 исполняются
   как 1-байтовый no-op; в Z80 на тех же местах — двухбайтовые
   `JR z/nz/nc/c, e`).

2. **Экспортёр печатал мнемонику, не сверяясь с байтом.**
   `export/asm_exporter.cpp` (`emitInstruction`) начинался с
   `os << "\t" << toLower(instr.mnemonic);`. `AnalyzedInstruction` уже содержит
   всё нужное — `uint8_t opcode` и `uint8_t size`
   (`agent/code_analyzer.h:31—40`, наполнение — `:181—182`). Для `28h` это
   `opcode=0x28`, `mnemonic="NOP", size=1` → текст `nop` → z80asm собирает `00h`.

3. **Класс дефекта общий, а не «один ROM».** `basic.r0m` задел только `28h`,
   потому что остальных семи опкодов в его кодовых диапазонах нет. Образ, где
   такие байты лежат как данные, не пострадает (данные идут через
   `defb`/`INCBIN`); пострадает любой ROM, где unassigned-opcode стоит на
   границе инструкции.

### Почему молчит только `NOP`-семейство

Для **истинно** неприсвоенных опкодов (`CBh, D9h, DDh, EDh, FDh, FFh`) в
дизассемблере уже был формат `F_DB` (`src/disassembler.cpp:293—296`): мнемоника
`DB` носит сам байт операндом, `convertOperands` превращает его в `db 0cdh`, и
round-trip не ломается. Дефект состоял ровно в том, что `NOP`-семейство
использовало `F_IMP` — формат, который байт не несёт.

Остальные 1-байтовые опкоды (`HLT`, `PCHL`, `XTHL`, `SPHL`, …) при расхождении
мнемоники с `-m=8080_strict` дали бы ошибку сборки, то есть видны немедленно.
Молча подменялся только `NOP`.

## Домен: это 8080, а не Z80 (важно для выбора фикса)

Проверено на самом эмуляторе, а не по мнемоникам:

- `debug_get_registers` отдаёт только `PC SP A F B C D E H L AF BC DE HL` — нет
  `AF'`/`BC'`/`DE'`/`HL'`, `IX`, `IY`, `I`, `R`;
- микро-зонд: в RAM на `0x7000` записано `28 05 …`, `PC=0x7000`, `debug_step`
  при `F=00h` и при `F=40h` (`Z`=0/1) — **в обоих случаях `PC=0x7001`**
  (байт+1). Настоящий `JR Z` при `Z=1` дал бы `0x7007`;
- то же на реальном месте образа: `PC=0x0AA7` (`28 CD`) → `PC=0x0AA8` при обоих
  состояниях `Z`.

Вывод: декод дизассемблера (`NOP`, size 1) **верен** для этой машины. Неверен
только вывод в ASM. Поэтому фикс обязан оставаться побайтовым, а не «починить
декод под Z80».

## Что уже исключено экспериментом

Правка классификации со стороны клиента **не помогает**. Заведены три объекта в
RDB (`debug_add_rdb_object`, тип `Data`, `size=1`, затем `debug_save_rdb`):
`data_0aa7`, `data_0ae9`, `data_1cb5`. Результат до фикса:

- экспортёр увидел объект и напечатал метку (`layout.asm`):

  ```asm
  func_0aa6:
      rst     func_0008
  data_0aa7:
      nop              ; ← должно быть defb 28h
      call    func_09b1
  ```

- вердикт `roundtrip_verify` не изменился (те же 3 байта).

То есть метка из RDB respected, а **тип `Data` внутри кодового диапазона —
нет**: байт по-прежнему выводится мнемоникой инструкции (побайтовое владение
из Stage 6.23 §2.4 отдаёт приоритет коду). Исправление требовалось в экспортёре.

## Resolution

Локализовано в экспортёре, по тому же принципу, что уже применялся к формату
`DB`: если мнемоника не воспроизводит исходный байт — печатать байт.

1. `export/asm_exporter.h` / `export/asm_exporter.cpp` — новый публичный
   статический хелпер `AsmExporter::unassignedOpcodeRow(instr)`: при
   `mnemonic == "NOP" && opcode != 0x00 && size == 1` возвращает строку
   комментария + `defb`-строку (`"\tdefb\t" + formatByte(opcode)`, стиль
   `emitByteRows`), иначе пустую строку. Публичный и статический — чтобы
   проверяться тестом напрямую, по образцу `convertOperands`/`formatByte`.
2. `emitInstruction` вызывает хелпер первым и при непустом результате
   возвращает его, не печатая мнемонику. Метки, комментарии и свойства RDB
   печатаются вызывающей стороной (`emitAddressLabel`), поэтому `data_0aa7:`
   остаётся на месте.
3. `formatByte()` закрывает ведущую цифру: `0x08 → 08h`, `0x28 → 28h`
   (`tests/test_asm_exporter.cpp`, тест `format_byte`).

Настоящий `NOP` (`00h`) печатается мнемоникой как раньше; `DB`-опкоды, `JMP`,
`HLT` и прочее — тоже.

### Тесты

`tests/test_asm_exporter.cpp`:

- `unassigned_opcode_row` — unit: все семь опкодов → `defb`-строка с корректным
  литералом и без `nop`; `00h`/`C3h JMP`/`76h HLT`/`DB` → пустая строка;
- `export_unassigned_opcodes` — интеграционный: синтетический ROM с семью
  неприсвоенными опкодами на пути анализа + настоящим `NOP` после них;
  проверяется, что в `layout.asm` каждый байт сохранён как отдельная
  `defb`-строка, каждый заменён под комментарием, `nop` в потоке ровно один
  (тот, что `00h`), и ни один литерал не начинается с буквы.

```
./build/test_asm_exporter
Results: 708 passed, 0 failed
```

### Проверка на исходном ROM

Экспорт `basic.r0m` (`--origin 0x0000`, RDB рядом с ROM) после пересборки
`v06c-asm-export`: три расхождения из `roundtrip_verify.json` — ровно три
подменённых места, все три сохранены:

```asm
data_0aa7:
        ; unassigned i8080 opcode, executes as NOP -- emitted as byte
        defb    28h
        call    func_09b1
```

Оставшиеся в `layout.asm` две инструкции `nop` стоят на байтах `00h`
(`0x1C5D`, `0x1C5E`) — то есть ложных срабатываний нет.

Окончательное подтверждение — побайтовый diff в пайплайне `vector-games`
(локально `z80asm` не установлен):

```bash
cmake --build /home/alexey/Projects/vector-debug/build --target v06c-asm-export
utils/analyze/run_pipeline.sh basic --from export_asm
```

Ожидание: `roundtrip_verify: SUCCESS` с `0 расхождений`.

## Чего делать не надо

Не менять `optable` на Z80-трактовку `28h → JR Z`. Это разошлось бы с
поведением эмулятора (см. «Домен») и изменило бы покрытие всех существующих
ROM.

## Известные границы

Закрыт именно класс «мнемоника не воспроизводит байт» для `NOP`-семейства —
того, что подтверждено кодом и наблюдавшимся расхождением. Универсальная
сверка «мнемоника+операнды → ожидаемый байт» для всех форматов (страховка от
будущих расхождений декодера, при несовпадении — `defb`-последовательность
длиной `instr.size`) сознательно **не** реализована: объём правки не оправдан,
пока все остальные классы либо round-trip'ятся (`DB`), либо падают в
`syntax_check` явно.
