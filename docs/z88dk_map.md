# Z88DK MAP File Format

## Overview

Z88DK generates `.map` files during linking when the `-m` flag is passed to `zcc` or `z80asm`.
The MAP file lists all symbols (labels, constants, functions, variables) with their addresses,
visibility, source module, section, and source location.

The MAP file is a **plain text file** with one symbol per line.

Status: VERIFIED_BY_SOURCE (Z88DK test suite `src/z80asm/t/option_map.t`, real MAP files)

## File Naming

The MAP file has the same basename as the output binary with a `.map` extension:

```
program.rom  →  program.map
fire.bin     →  fire.map
```

Generated by `z80asm` when invoked with `-m` flag. The `zcc` frontend passes `-m` to the
linker when the user specifies `-m` or when debug info generation is enabled.

Status: VERIFIED_BY_SOURCE (zcc.c: "z80asm now generates map file with same basename as output binary")

## Line Format

Each symbol line has the following structure:

```
<symbol_name_padded>            = $<HEX4> ; <type>, <visibility>[, <def>][, <module>, <section>, <source_location>]
```

### Formal Grammar

```
map_line    = symbol_name padding "= $" hex4 " ; " fields
symbol_name = identifier                          ; 1–32 characters
padding     = <spaces to align "= $" at column 34>
hex4        = 4 uppercase hex digits [0-9A-F]
fields      = type ", " visibility [", " def] [", " module] [", " section] [", " source_loc]
```

### Field Positions

The `= $` pattern is aligned at **column 34** (0-indexed: column 33). Symbol names are
left-aligned and padded with spaces to fill 32 characters, followed by 2 spaces before `=`.

Status: VERIFIED_BY_SOURCE (all real MAP files confirm 32-char name field + " = $")

## Fields

### 1. Symbol Name

- Left-aligned, padded with spaces to 32 characters
- Can contain: letters, digits, underscores `_`, dots `.`, at-signs `@`
- C functions are prefixed with `_` (e.g., `_main`, `_gfx_clear`)
- Assembly labels have no leading underscore (e.g., `start`, `call_hl`, `isr_done`)
- Compiler-generated linker symbols start with `__` (e.g., `__head`, `__size`)
- Local labels in C (loop counters, etc.) have short names (e.g., `i_4`, `i_10`)
- Names are case-sensitive

Status: VERIFIED_BY_SOURCE

### 2. Address

- Format: `$HHHH` — dollar sign prefix followed by exactly **4 uppercase hex digits**
- Range: `$0000` to `$FFFF` (16-bit address space)
- No `0x` prefix, no suffix `h`
- Always zero-padded to 4 digits

Status: VERIFIED_BY_SOURCE (Z88DK `int_to_hex` uses `$` prefix, width 4)

### 3. Type

| Value   | Meaning |
|---------|---------|
| `addr`  | Code or data label — represents a memory address with actual content |
| `const` | Compile-time constant — does NOT represent a memory location |

**Critical distinction:** `const` entries are NOT memory addresses. They are values computed at
link time. For example, `__head = $0100 ; const` means the program starts at address 0x0100,
but `__head` itself is not stored in memory. A `const` at `$0100` does NOT block an `addr`
symbol at the same address.

Status: VERIFIED_BY_SOURCE

### 4. Visibility

| Value    | Meaning |
|----------|---------|
| `public` | Exported symbol — visible to other modules |
| `local`  | Internal symbol — visible only within its module |

Both `public` and `local` symbols appear in the MAP file. Local symbols include assembly labels,
loop counters, and internal function labels.

Status: VERIFIED_BY_SOURCE

### 5. Def (optional)

| Value  | Meaning |
|--------|---------|
| `def`  | Symbol was explicitly declared as PUBLIC/EXTERN (defc alias) |
| empty  | Regular symbol definition |

Present only for `defc` aliases and explicitly exported symbols. Regular labels and C functions
have this field empty. In the formatted output, empty fields appear as spaces between commas.

Status: VERIFIED_BY_SOURCE (option_map.t: `defc alias_main = main` → `def` field present)

### 6. Module (optional)

The source module name where the symbol is defined. Examples:

| Module name | Origin |
|-------------|--------|
| `main_c` | main.c compiled to assembly |
| `startup_asm` | startup.asm |
| `clr_asm` | clr.asm |
| `v06io_asm` | v06io.asm |
| `X______lib_gfx_mode_c` | ../../lib/gfx/mode.c (mangled path) |
| `l_div_u` | l_div_u.asm (library module) |
| `test_t_option_map_t` | test file (auto-generated module name from filename) |

Module names derived from C files: take the filename, replace `.` with `_`, append `_c`.
Module names from asm files: take the filename without extension, replace non-identifier chars with `_`.
Long paths are mangled: `../../lib/gfx/mode.c` → `X______lib_gfx_mode_c`.

Status: VERIFIED_BY_SOURCE

### 7. Section (optional)

The section where the symbol's code/data is placed. Common sections:

| Section | Content type |
|---------|-------------|
| `code_clib` | C library code |
| `code_compiler` | User C compiler code |
| `code_l_sccz80` | sccz80 compiler support library code |
| `code_user` | User-defined code sections |
| `rodata_compiler` | Read-only data from C compiler |
| `data_compiler` | Initialized data from C compiler |
| `data_user` | User-defined data sections |
| `bss_compiler` | Uninitialized data (BSS) from C compiler |

For `const` type symbols, the section field is typically empty.

Status: VERIFIED_BY_SOURCE

### 8. Source Location (optional)

Points to the source file and line where the symbol is defined. Two formats:

**C function:**
```
file.c::function_name::N::M:line
```
- `file.c` — source file name (may include relative path)
- `function_name` — C function name
- `N` — (internal counter, usually 0)
- `M` — (internal counter, varies)
- `line` — line number in source file

**Assembly label:**
```
file.asm:line
```
- `file.asm` — assembly source file (may include relative path like `../../lib/sys/startup.asm`)
- `line` — line number in source file

Status: VERIFIED_BY_SOURCE

## Standard Linker Symbols

Every Z88DK MAP file contains these linker-generated constants:

| Symbol | Type | Meaning |
|--------|------|---------|
| `__head` | const | Program start address |
| `__size` | const | Total program size in bytes |
| `__tail` | const | Program end address (head + size) |

Per-section boundary symbols:

| Pattern | Meaning |
|---------|---------|
| `__<section>_head` | Section start address |
| `__<section>_size` | Section size in bytes |
| `__<section>_tail` | Section end address |

Examples from real MAP files:
```
__code_clib_head                = $014A ; const, public, def, , ,
__code_clib_size                = $0147 ; const, public, def, , ,
__code_clib_tail                = $0291 ; const, public, def, , ,
__rodata_compiler_head          = $0291 ; const, public, def, , ,
__data_compiler_head            = $0519 ; const, public, def, , ,
__bss_compiler_head             = $051B ; const, public, def, , ,
```

Status: VERIFIED_BY_SOURCE

## Complete Real Examples

### Example 1: Linker constants (const entries)

```
__head                          = $0100 ; const, public, def, , ,
__size                          = $047E ; const, public, def, , ,
__tail                          = $057E ; const, public, def, , ,
```

Fields breakdown for `__head`:
- Symbol name: `__head` (padded to 32 chars)
- Address: `$0100`
- Type: `const` (compile-time constant, not a memory location)
- Visibility: `public`
- Def: `def` (explicitly defined)
- Module: empty
- Section: empty
- Source location: empty

### Example 2: C function (public addr)

```
_main                           = $025F ; addr, public, , main_c, code_clib, main.c::main::0::1:109
```

Fields breakdown:
- Symbol name: `_main`
- Address: `$025F`
- Type: `addr` (actual code address)
- Visibility: `public`
- Def: empty (regular definition, not a defc alias)
- Module: `main_c`
- Section: `code_clib`
- Source location: `main.c::main::0::1:109` (function `main` in `main.c`, line 109)

### Example 3: Assembly label (local addr)

```
start                           = $0100 ; addr, local, , startup_asm, , ../../lib/sys/startup.asm:34
```

Fields breakdown:
- Symbol name: `start`
- Address: `$0100`
- Type: `addr`
- Visibility: `local`
- Def: empty
- Module: `startup_asm`
- Section: empty
- Source location: `../../lib/sys/startup.asm:34`

### Example 4: defc alias (public addr with def)

```
alias_main                      = $0000 ; addr, public, , test_t_option_map_t1, , test_t_option_map_t1.asm:6
```

This was generated by `defc alias_main = main` in the source.

### Example 5: const does not block addr at same address

```
STACK_TOP                       = $0100 ; const, local, , startup_asm, , ../../lib/sys/startup.asm:26
start                           = $0100 ; addr, local, , startup_asm, , ../../lib/sys/startup.asm:34
```

Both symbols have address `$0100`. `STACK_TOP` is a compile-time constant (the initial stack
pointer value), while `start` is the actual entry point code at that address. The debugger
must load `start` (addr) and skip `STACK_TOP` (const).

### Example 6: Duplicate addresses (different symbols)

```
exit                            = $0129 ; addr, local, , startup_asm, , ../../lib/sys/startup.asm:60
exit_loop                       = $0129 ; addr, local, , startup_asm, , ../../lib/sys/startup.asm:61
```

Two different symbols at the same address — this is normal and expected.

### Example 7: Module name mangling for paths

```
_gfx_set_mode                   = $02BD ; addr, public, , X______lib_gfx_mode_c, code_compiler, ../../lib/gfx/mode.c::gfx_set_mode::0::0:39
```

The module name `X______lib_gfx_mode_c` is a mangled form of the path `../../lib/gfx/mode.c`.

## File Structure

The MAP file is a flat list of lines with no sections, headers, or separators:

```
const entries (linker symbols, section boundaries)
...
addr entries (public and local, mixed)
...
```

The order is typically:
1. Linker-generated `const` entries (`__head`, `__size`, section boundaries)
2. `addr` entries sorted alphabetically by symbol name

Status: VERIFIED_BY_SOURCE (all real MAP files confirm this ordering)

## Format Validation

A valid Z88DK MAP file must contain at least one line with the `= $` pattern.
Lines without this pattern are not valid Z88DK MAP entries.

Non-Z88DK `.map` files (e.g., PSP key mapping configs) have completely different formats:
```
# Vector-06C PSP key mapping
version=1
PSP_X=1
```

These must NOT be parsed as Z88DK MAP files.

Status: VERIFIED_BY_SOURCE

## MAP vs .dbg

The `.map` file is an external Z88DK format described in this document.

The `.dbg` file is an internal debugger format (if used by the project).

They are NOT interchangeable. The AI Agent must not confuse them.

Status: VERIFIED_BY_CONVENTION

## Hardware vs Emulator Behavior

The MAP file format is a Z88DK toolchain artifact, not hardware behavior.
It is generated by the linker (`z80asm`) during compilation and has no relation
to the physical Vector-06C hardware. The format is the same regardless of target machine.

MAP file addresses correspond to the linked binary's address space, which for Vector-06C
ROMs starts at 0x0100 (standard .rom load convention).

## Recommendations for AI Agent

### Reading MAP files

1. Verify the file is a Z88DK MAP by checking for the `= $` pattern.
2. Parse each line according to the format above.
3. Distinguish `addr` (real addresses) from `const` (compile-time constants).
4. Do not assume symbol purpose from name alone — verify with disassembly.

### Generating MAP files

When asked to create or generate a MAP file:

1. Use the exact Z88DK format described above.
2. Pad symbol names to 32 characters.
3. Use `$HHHH` format with 4 uppercase hex digits.
4. Include all required comma-separated fields in the comment.
5. Do NOT use JSON, YAML, CSV, or any other format.
6. Do NOT invent fields or sections not described here.
7. If information is insufficient, report what data is missing.

### Do NOT

- Invent a custom MAP format.
- Create debugger-specific MAP syntax.
- Assume that any `symbol = value` text file is a Z88DK MAP.
- Use the debugger's internal `Symbol`/`Function`/`Section` structures as a "MAP format".
