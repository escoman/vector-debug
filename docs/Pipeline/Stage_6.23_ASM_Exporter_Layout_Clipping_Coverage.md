### 2.1 P0 — эмиттер не клиппирован окном ROM (фантомные 256 `nop`)

`code.asm` начинается с `; --- Code range: 0000 ---` и 256 инструкций `nop`.
Корень: seeds control-flow анализа включают `0x0000` — это намеренно (на железе
выполнение «стекает» по NOP-sled в 0x0000–0x00FF до входа в 0100h), и убирать его
из **анализатора** нельзя, иначе рассыплется граф достижимости.

**Фикс:** клиппинг в **эмиттере** — не выводить ни одной инструкции и ни одного
диапазона за пределами `[origin, origin + rom_size)`. Комментарий-заголовок
`asm_exporter.cpp` (сейчас гласит «from 0x0000») привести к «from entry points,
clipped to ROM window».

**Проверка:** в `code.asm` нет строки `Code range: 0000`, нет `nop`, не покрытых
адресом из окна ROM; первая эмитированная инструкция имеет адрес `origin`.

### 2.2 P0 — компоновка не воспроизводит образ

`emitMainAsm()`: один `.org origin` + `include "code/code.asm"` + `include "data/data.asm"`.
Данные идут блоком после всего кода, тогда как в ROM код и данные интерливингованы
(в TESTAY: `var_music_ptr @0x0103` внутри кода, таблицы в `0x04xx`, музыкальные
дорожки в середине образа). Второй `.org` для падинга невозможен — **z80asm
разрешает `org` только один раз на модуль** («ORG redefined»).

**Фикс:** эмитировать единый адресно-упорядоченный поток: единицы вывода
(инструкция, блок данных, gap) сортируются по адресу, между соседними единицами
проверяется непрерывность; при разрыве вставляется `ds`/`defb` на непокрытые байты
(см. 2.3) вместо тихого сдвига. `code.asm`/`data/data.asm` допустимо оставить как
удобочитаемые view, но в сборку должен идти `layout.asm` (или `main.asm` без split).

**Проверка:** длина собранного образа == `rom_size`; совпадение байт 1:1 (см. §3).
Достижимость подтверждена практикой: тот же текст экспорта, разложенный по
адресам через `defs`, собирается в побайтово точный образ (`.rt/exact.rom`,
3712 байт, 0 отличий) — значит фикс реализуем именно так.

### 2.3 P1 — потеря кода не обнаруживается (главный риск)

**Уточнение причины (замер 15.09, RDB с 63 объектами).** Ранняя формулировка
«вход только через вычисляемый `PCHL`» неверна. Настоящая причина —
control-flow анализатор не идёт по условным переходам (см.
`TZ-mcp-agent-api.md` §7): линейный проход обрывается на границе, за которой
код достижим только `Jcc`. Семена из RDB (каждая функция — seed) это лечит
частично: пока анализировались только `JMP`/`CALL`, терялось 170 байт.

Текущий замер (`asm/`, RDB 65 объектов; покрыто кодом 1069 байт + данными 2643,
вместе = 3712 = 100 % окна ROM):

| Интервал | Байт | Что это | Статус |
|---|---|---|---|
| 0x023C–0x02C2 | 135 | обработчики событий | **покрыто** после seeds из RDB |
| 0x04BB–0x04CC | 18 | хвост главного цикла | **покрыто** |
| 0x053D–0x053E | 2 | мёртвые `EI; RET` | **покрыто** |
| 0x032E–0x0331 | 4 | `XRA A; STA 049C`, цель `JZ 032E` **внутри** функции | закрыто вручную (ниже) |
| 0x0437–0x0441 | 11 | расчёт комплемента тона, цель `JZ 0437` **внутри** функции | закрыто вручную (ниже) |

Оба последних прокола — условные цели в середине уже засеянной функции. Их удалось
закрыть **без фикса анализатора**: в RDB добавлены два объекта типа `Label`
(`code_envelope_clear` @0x032E, `code_period_difference` @0x0437), они попали в
seeds (`asm_exporter.cpp:207-209`), после чего покрытие стало 100 %, а операнды
`jz` получили имена вместо сырых `032Eh`/`0437h`. Побочный вывод, важный для
регламента: **`Label`-объекты в RDB — штатный способ залатать слепые зоны
анализатора**, и пока §7 `TZ-mcp-agent-api.md` не починен, экспорт вынужден
опираться на ручной труд. Дефект анализатора от этого не исчезает: без двух
вручную найденных меток 15 байт пропали бы молча.

Симптом-обманка из прошлого замера (`unknown_04CD` там, где был потерян
`JMP 049Dh`) исчез: 0x04BB–0x04CC теперь эмитируется. Монотонный индекс в цикле по `analysis_.ranges` при этом всё ещё молча теряет инструкции при
несортированных или перекрывающихся диапазонах.

`export.json` при этом рапортует `warnings: 0`. **Без отчёта о покрытии потеря
неотличима от успеха — это самый опасный дефект инструмента.**

**Фикс (минимально достаточный):**
1. Считать `uncovered = [origin, origin+size) \ (код ∪ данные)`.
2. В `export.json` добавить `coverage: { rom_bytes, code_bytes, data_bytes,
   uncovered: [{start,end}], instruction_count, complete: bool }`.
3. При `!complete` — `WARNING` в консоль и ненулевой exit code (либо флаг
   `--strict`, обязательный в CI). Сейчас `warnings: 0` при 170 потерянных байтах.
4. Непокрытые интервалы эмитировать как `gap_%04X` (`defb`/`ds`), сохраняя
   непрерывность образа — чтобы прогон всё равно давал собираемый и побайтово
   точный результат, но с явными метками подозрения.
5. Seeds анализа расширить эвристикой таблиц переходов: если `PCHL`/`JMPHL`
   предваряется загрузкой base-адреса (`LXI H,nn00h` / `DAD` + `PCHL`), помечать
   страницу `nn00–nnFF` как кандидат-код. В TESTAY диспетчер считает
   `HL = 0x0700 + (E−B)` и уходит в страницу музыкальных данных.

**Проверка:** `coverage.complete == true`, `uncovered == []` для TESTAY.ROM;
`instruction_count` == 871 (столько же, сколько даёт текущий экспорт с двумя
`Label`-seeds); при удалении этих seeds покрытие обязано упасть на 15 байт и
`complete` обязан стать `false` — это и есть тест на «потеря не молчит».

### 2.4 P2 — объекты типа `Variable` не участвуют в экспорте

`asm_exporter.cpp:205-213` сеет анализ по `Function`/`Label`/`Code`,
`:235-245` берёт имена, `:294-300` — диапазоны данных из `Data`/`Table`/`String`.
`Variable` не проходит ни по одному фильтру, поэтому все 24 переменных RDB в TESTAY
(0x0101 `var_main_loop_target`, 0x0103 `var_track_ptr`, 0x045E..0x0464,
0x0466/0x0467/0x0468, 0x0469/0x046B/0x046D, 0x048F..0x049C, 0x04A2) в выводе
получают автоимя разрыва:

```
data.asm:  unknown_0103:  defb 0FBh,0C9h      ; должен быть var_track_ptr
data.asm:  unknown_045E:  ...                 ; var_ptr_045e/0460/0462/0464
data.asm:  unknown_0490:  ...                 // var_ay_ch_b_period и далее
code.asm:  lhld    04a2h                      ; должен быть lhld var_delay_loop_seed
```

Данные при этом эмитируются (разрывы заполняются `defb`), так что на побайтовую
точность это не влияет — теряет только читаемость и переиспользуемость имён
в Stage 3.

**Фикс:** включить `Variable` (и `Unknown`) в выборку имён и в список диапазонов;
в операндах инструкций подставлять имя переменной по адресу операнда
(сейчас подставляются имена только `Function`).

**Проверка:** в `data.asm` нет меток `unknown_%04X` по адресам, где в RDB стоит
объект с именем; в `code.asm` встречается `lhld var_delay_loop_seed`,
а не `lhld 04a2h`.

## 3. Критерий приёмки (один, машинный)

```bash
v06c-asm-export --rom TESTAY.ROM --rdb TESTAY.rdb --output out/
z80asm -m=8080_strict -b -o=out.rom out/main.asm     # 0 ошибок, 0 warnings
cmp -s TESTAY.ROM out.rom                            # TRUE — побайтовое равенство
```

Ожидаемый референс после фикса: `out.rom` = 3712 байта, идентичен исходному ROM.
Любые «почти совпало, кроме N байт» считаются непройдёнными.

Контрольная точка (уже измерено 15.09): если из текущего экспорта убрать
фантомные 256 `nop` и расставить куски по адресам через `defs`, получается
**побайтово точный** образ. То есть критерий ниже достижим правкой компоновки
(§2.1, §2.2) и ничего больше менять не нужно.

Тесты: round-trip на синтетическом ROM (`full_export_synthetic`) прогонять через
реальный `z80asm`, если он доступен в CI; иначе — зафиксировать ожидаемый hex-dump.
Фикстуры `convert_operands_*` обязаны передавать операнды **в том виде, в котором их
выдаёт `disassemble()`** (с пробелом после запятой: `"B, 082A"`), иначе тесты снова
будут зелёными поверх сломанного кода — именно так произошло с прошлой партией.
