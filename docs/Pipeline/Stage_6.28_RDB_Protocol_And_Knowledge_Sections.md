# Stage 6.28 — RDB: разделы знания (Protocol / Ports / Watch-list)

*Происхождение: разбор `docs/Skoolkit_HATE_Lessons.md` (практики SkoolKit, уроки сессии H.A.T.E.)
и обсуждение «журнала гипотез» для агента. Stage описывает, что добавляется в **RDB** как
хранилище, чтобы реализовать P5+L1 (порт-таблица + автокомментарии) и предложение пользователя —
раздел протокола проверки гипотез. Инструменты MCP/Agent API упоминаются только как обязательные
ворота к этим данным; сами дизассемблер/экспортёр здесь не меняются.*

---

## 1. Цель

Превратить RDB из «базы объектов ROM» в «базу знаний о ROM», добавив три новых
верхнеуровневых раздела рядом с существующим `objects`:

```text
protocol   — журнал проверки гипотез (тезис + статус + улика), append-only
ports      — таблица портов/регистров аппаратуры с полярностью и семантикой битов
watchlist  — именованные наблюдаемые переменные для чекпоинтов/брейкпоинтов
```

Плюс **конвейер промоции**: подтверждённая запись `protocol` становится источником
для `ports` / комментариев объектов. Это связывает «черновое знание» (журнал) и
«компилированное знание» (таблицы, автокомментарии P5).

Решаемые проблемы из урока:

| Урок | Что даёт раздел |
|------|-----------------|
| L1 — полярность портов съела 6 дней прогонов | `ports` с явной полярностью и семантикой битов |
| L4 — чекпоинт без значений переменных бесполезен | `watchlist` |
| P5 — листинг читается как псевдокод | `ports` → автокомментарии (реализация вне этого stage, но данные — здесь) |
| «агент каждый раз начинает с чистого листа» | `protocol` |

## 2. Главные принципы (наследуются из Stage 6.11)

* RDB Controller — единственный владелец содержимого `.rdb`; JSON не выходит наружу.
* GUI / Agent API / MCP работают только через типизированный API.
* Не сохранять после каждой операции; `dirty` + явный `save()`; atomic save.
* Новый раздел — **данные**, а не compile-time зависимость. Platform-specific
  (Вектор) живёт в значениях, не в ветвлении кода контроллера.
* Обратная совместимость: файл `version: 1` (без новых разделов) обязан грузиться;
  отсутствующие разделы читаются как пустые.

## 3. Формат и версионирование

Формат RDB поднимается с `version: 1` до `version: 2`.

Правила:

* `version: 2` отличается **только наличием необязательных разделов** `protocol`,
  `ports`, `watchlist`. Структура `objects` не меняется.
* Загрузчик принимает `version <= 2`. Для `version: 1` новые разделы считаются пустыми,
  файл остаётся валидным, `dirty` не выставляется.
* Сохранение всегда пишет `version: 2`, если хотя бы один новый раздел непустой;
  иначе сохраняет исходную версию (не «апгрейджить» молча файлы, которых не касались).
* `agent/knowledge/rdb_format.md` — единственный канонический описание формата —
  должен быть обновлён новыми разделами (см. §10).
* Capability: каждый новый класс инструментов MCP бампает `v06c.api_version`
  (сейчас 5 → 6, см. §8). Клиент не должен угадывать наличие разделов по версии бинаря —
  определять через `tools/list`.

Верхнеуровневая форма:

```json
{
  "format": "rdb",
  "platform": "vector06c",
  "version": 2,
  "rom": { "file": "game.rom", "size": 32768, "sha256": "..." },
  "objects": [ ... ],
  "protocol": [ ... ],
  "ports": [ ... ],
  "watchlist": [ ... ]
}
```

## 4. Раздел `protocol` — журнал гипотез

### 4.1. Назначение

Эмпирические находки реверс-инжиниринга с доказуемым статусом. Агент в начале сессии
читает активные записи и **не перепроверя то, что уже подтверждено или опровергнуто**.

Это НЕ комментарии к инструкциям и НЕ описание ROM. Это журнал *утверждений*, у каждого
есть время, метод проверки и улика.

### 4.2. Поля записи

Каждый элемент `protocol` — объект со следующими полями.

```json
{
  "id": "P-0001",
  "timestamp": "2026-10-27T14:32:10Z",
  "thesis": "Порт клавиатуры 0x01 активно-низкий: нажатая клавиша = 0-бит",
  "status": "VERIFIED_BY_TRACE",
  "scope": "hardware",
  "address": null,
  "method": "trace",
  "evidence": "breakpoint @0x1234: после debug_press_key('X') ROM-читатель видит бит 2=0; см. run_42 snapshot",
  "links": [],
  "supersedes": null,
  "superseded_by": null
}
```

| Поле | Обязательное | Тип | Значение |
|------|:---:|------|----------|
| `id` | да | string | стабильный уникальный идентификатор записи; присваивает контроллер |
| `timestamp` | да | string | ISO-8601 UTC, время внесения |
| `thesis` | да | string | тезис одной строкой (нормализуется через `normalizeRdbText`) |
| `status` | да | enum | см. §4.3, закрытый список |
| `scope` | да | enum | `rom` / `hardware` / `tooling` (см. §4.5) |
| `address` | нет | hex/null | привязка к адресу ROM, если она есть |
| `method` | нет* | enum | `trace` / `diff` / `primary-source` / `golden-test` / `static` |
| `evidence` | нет* | string | **улика**: адреса, имена снапшотов, какой тест прошёл |
| `links` | нет | array | id других записей protocol (подтверждает/противоречит) |
| `supersedes` | нет | id/null | эта запись замещает ту |
| `superseded_by` | нет | id/null | эта замещена той (поддерживается контроллером) |

\* См. §4.4 — для статусов VERIFIED*/REFUTED поля `method` и `evidence` **обязательны**.

### 4.3. Статусы — закрыть и переиспользовать

Не изобретать новый словарь. Берём классификацию из
`agent/knowledge/vector06c/verification.md` (§ «Классификация статусов») и адаптируем
под трассировку ROM:

| Статус | Смысл | method/evidence обязателен |
|--------|-------|:---:|
| `VERIFIED_BY_TRACE` | подтверждено исполнением (трасса/брейкпоинт) | да |
| `VERIFIED_BY_SOURCE` | подтверждено первичной документацией/TIMSoft | да |
| `VERIFIED` | подтверждено несколькими независимыми методами | да |
| `PARTIALLY_VERIFIED` | подтверждена часть утверждения | да |
| `CONFLICT` | источники/ прогоны противоречат | да |
| `UNVERIFIED` | подтверждения не найдено | нет |
| `REFUTED` | опровергнуто (см. §4.6) | да |
| `SPECULATION` | предположение без улик | нет |

Требования:

* Закрытый enum. Контроллер обязан отклонить неизвестное значение (`InvalidArgument`).
* Свободнотекстовый статус запрещён — иначе за две недели накопится «Опровергнут (probably)».
* `normalizeRdbText` применяется к `thesis` и `evidence` (переносы строк схлопываются —
  журнал не должен ломать сериализацию, как уже сделано для comments в Stage 6.11).

### 4.4. Правило «нет улик — нет подтверждения»

Контроллер **не даёт** выставить `VERIFIED*` / `REFUTED` без заполненных `method` +
`evidence`. Это центральное отличие от «списка комментариев»: журнал без улик
деградирует в слухи, а доверять слухам опаснее, чем не доверять ничему (ровно баг L1:
ложные данные выглядели правдоподобно). Попытка записать подтверждение без улик → ошибка.

### 4.5. `scope` — почему не всё привязано к адресу

Часть самых ценных тезисов — не о ROM:

* L1 (баг инжектора: OR без инверсии) → `scope: tooling`;
* L9 (сначала верифицируй стенд) → `scope: tooling`;
* полярность клавиатурного порта Вектора → `scope: hardware`.

У них нет `address`. Поэтому `address` опционален, а `scope` обязателен:

```text
rom       — утверждение о конкретном ROM (проверять при совпадении sha256, §7)
hardware  — утверждение об аппаратуре Вектора (ездит между ROM)
tooling   — утверждение об инструменте/стенде (ездит между всем)
```

### 4.6. Append-only и «замещено» (supersede)

Журнал **только дополняется**. Правка/удаление подтверждённой истории запрещены.

Кейс из урока (L2): «ctl-разметка $D000+ = упакованная графика» была `VERIFIED_BY_TRACE`,
потом опровергнута чекпоинтом `PC=$E2D7`. Старую запись нельзя стереть — иначе теряем,
почему план был такой.

Правильная операция:

```text
addProtocolEntry(thesis="..., графика", status=REFUTED, supersedes="P-0007")
  ↓ контроллер:
  помечает P-0007.superseded_by = новый id
  новый id остаётся активным
```

`status: REFUTED` + `supersedes` — это и есть «опровергнуто позже», без переписывания
истории. Удаление записи из API допускается только как явная операция
`removeProtocolEntry(id)` с запретом на удаление записи, на которую ссылается `supersedes`
другой активной записи.

### 4.7. Дедупликация

Перед `addProtocolEntry` — обязательный поиск. Инструмент `getProtocol` фильтрует по:

```text
substring(thesis)
address
scope
status
```

Правило агента (§11): нашёл похожий активный тезис → обновляй статус/ссылку, а не плоди
третью запись про полярность клавиш.

## 5. Раздел `ports` — таблица портов и семантики битов

### 5.1. Назначение

L1 прямо требует: «документированная таблица „порт → бит → смысл, активный уровень“
должна быть частью RDB, а не памяти агента». Это скомпилированное знание — источник для
автокомментариев P5 и для осмысленного view I/O.

### 5.2. Форма записи

```json
{
  "port": "0x01",
  "name": "keyboard_strobe",
  "direction": "input",
  "polarity": "active-low",
  "bits": [
    { "index": 0, "meaning": "K1 / KEY0" },
    { "index": 7, "meaning": "shift/CAPS" }
  ],
  "comment": "Нажатая клавиша = 0-бит; инжектор обязан инвертировать маску"
}
```

| Поле | Тип | Notes |
|------|-----|-------|
| `port` | hex | адрес порта/регистра (0x0C–0x0F палитра, звук, ППО/МС и т.д.) |
| `name` | string | символическое имя |
| `direction` | enum | `input` / `output` / `in-out` |
| `polarity` | enum | `active-high` / `active-low` / `n/a` |
| `bits[]` | array | `{index, meaning}` — семантика каждого бита |
| `comment` | string | свободное пояснение (normalizeRdbText) |

### 5.3. Требования

* Один объект на `port` (уникальность как у `objects` по address, Stage 6.26 §14).
* Значения enum закрытые; неизвестный `polarity`/`direction` → `InvalidArgument`.
* Раздел платформенный по данным, но не по коду: структура портов не должна
  хардкодить Вектор в RDB Controller (данные приходят через API, контроллер их не
  интерпретирует — §2, Stage 6.11 §38).
* `ports` — кандидаты на генерацию автокомментариев дизассемблера (P5):
  `IN 0x01` → «читает keyboard_strobe, active-low». Сама генерация — отдельный
  последующий stage; здесь только данные-источник.

## 6. Раздел `watchlist` — наблюдаемые переменные

### 6.1. Назначение

L4: чекпоинт/брейкпоинт должен печатать значения именованных переменных, а не только PC.
Это дешёвая надстройка, многократно ускоряющая «прогон → диагноз».

### 6.2. Форма

Watch-point ссылается на существующий RDB `Variable`-объект (тип `variable` уже есть),
либо задаёт адрес/диапазон явно:

```json
{
  "name": "score",
  "address": "0x2010",
  "length": 2,
  "format": "uint16-le",
  "object_address": "0x2010"
}
```

| Поле | Notes |
|------|-------|
| `name` | отображается в логе чекпоинта |
| `address` / `length` | диапазон памяти |
| `format` | `uint8` / `uint16-le` / `int8` / `bcd` / `bits` и т.п. |
| `object_address` | необязательная ссылка на существующий RDB-объект (тогда имя/тип берутся оттуда; watch — лишь «включить в печать») |

### 6.3. Требования

* `watchlist` не дублирует объект: если есть `object_address`, данные переменного —
  в `objects`, здесь только решение «печатать в чекпоинт + формат».
* Реализация печати в брейкпоинт-лог / checkpoint-лог — вне хранения RDB (backend /
  MCP). Stage фиксирует только **где живут списки наблюдения** (RDB, ездят с ROM).

## 7. ROM identity и несовпадение (protocol)

RDB привязан к ROM через `rom.sha256` (Stage 6.11 §5). Значение для `protocol`:

* При загрузке ROM с другим `sha256` активные записи `scope: rom` **не должны молча
  применяться** к новому ROM. Контроллер/API обязан сообщить состояние mismatch
  (уже предусмотрено: «Состояние mismatch доступно через API», Stage 6.11 §5).
* `scope: hardware` / `tooling` — не зависят от sha256 и остаются валидными.
* Задача агента: при mismatch перепроверять `scope: rom`-тезисы, а не считать их
  унаследованными.

## 8. API: RDB Controller → Agent API → MCP

### 8.1. RDB Controller (типизированные операции, JSON наружу не выходит)

```text
Protocol
  addProtocolEntry(entry) -> id
  updateProtocolStatus(id, status, method, evidence)
  supersedeProtocolEntry(oldId, newEntry)
  getProtocol(filter{scope,status,address,substring}) -> list
  removeProtocolEntry(id)

Ports
  upsertPort(portEntry)
  getPort(port)
  listPorts()

Watchlist
  addWatchEntry(watch)
  removeWatchEntry(name|address)
  listWatch()
```

Все изменяющие операции устанавливают `dirty = true` только при реальном изменении
(Stage 6.11 §5, §13). Чтение — никогда.

### 8.2. Agent API

тонкое отображение Controller API, ничего не решает сам.

### 8.3. MCP (тонкий протокольный адаптер, без логики)

```text
debug_add_protocol_entry
debug_get_protocol
debug_supersede_protocol_entry
debug_upsert_port
debug_get_ports
debug_add_watch_entry
debug_list_watch
debug_remove_watch_entry
```

* MCP только сериализует `AgentApiResult<T>` / `ErrorCode` (Stage 6.26 §19).
* `tools/list` обязан показывать новые инструменты; `v06c.api_version` 5 → 6.
* Лимиты: `debug_get_protocol` имеет `max_entries` и фильтрацию по статусу —
  иначе при 200 записях это дамп, съедающий контекст агента.

## 9. Конвейер промоции (связка protocol → ports/comments)

Это то, что не даёт журналу стать вторым конкурирующим источником истины.

```text
protocol (черновик, есть улика)
    │  статус VERIFIED_BY_TRACE / VERIFIED_BY_SOURCE
    ↓  промоция
compiled knowledge:
    • scope=hardware  → запись в ports
    • scope=rom + address → comment/property объекта в objects
```

Правила:

* Промоция **не удаляет** запись protocol — она помечает её промотированной
  (`links` на объект/порт) и оставляется как источник/история.
* Единственный легальный источник данных для `ports` и автокомментариев P5 —
  **подтверждённые** записи protocol. Нельзя вносить знание о полярности сразу в
  `ports`, минуя журнал (иначе теряем «когда и чем доказано»).
* Исключение: первичная загрузка канонической таблицы портов Вектора (bulk-import из
  knowledge base) — оформляется как одна `VERIFIED_BY_SOURCE` запись-основание.

## 12. Тестирование

### Unit (RDB Controller)

```text
protocol:
  add → id присвоен, dirty=true
  VERIFIED* без method/evidence → ошибка (§4.4)
  неизвестный status/scope → InvalidArgument
  supersede: у старой записи проставлен superseded_by, новая active
  remove записи, на которую ссылается supersedes → запрещено
  getProtocol фильтры: scope / status / address / substring
  normalizeRdbText применяет thesis/evidence (переносы → пробел)
ports:
  upsert уникален по port
  неизвестный polarity/direction → InvalidArgument
watchlist:
  add/remove/list; ссылка на object_address не дублирует объект
совместимость:
  load version:1 (без разделов) → пустые разделы, dirty=false
  save версии 2 только если хотя бы один новый раздел непустой
  save when clean → без лишней перезаписи
  atomic save сохраняет новые разделы и перезагружает их идентично
```

### Integration

```text
Реальная цепочка MCP → Agent API → RDB Controller → filesystem (не mock).
Сценарий L1: upsert keyboard port active-low → round-trip save/load.
Сценарий L2: VERIFIED_BY_TRACE → supersede REFUTED с уликой → getProtocol(active)
              не показывает замещённую, история сохранена на диске.
```

### Regression

```text
test_agent_api / test_agent_commands / test_agent_contract — проходят.
Существующие RDB tests (Stage 6.11/6.13) — проходят, version:1 грузится.
Существующие MCP tools не сломаны.
```

## 13. Что НЕ делать на этом stage

* Не менять дизассемблер и экспортёр (генерация автокомментариев P5 — отдельный stage;
  здесь только данные-источник в `ports`).
* Не реализовывать печать watch-list в брейкпоинт-лог (backend-работа, отдельный этап;
  здесь — где живут списки).
* Не класть семантику анализа ROM в MCP (Stage 6.26 §2): сервер предоставляет данные,
  не принимает решений о code/data и не выводит Fact/Inference.
* Не делать protocol как `RdbObjectType` (типа `Claim`): `RdbObject` жёстко привязан к
  `address` и описывает фрагмент ROM, а protocol — про утверждения без адреса.
  Это отдельный верхнеуровневый раздел.
* Не добавлять RAG / embeddings / vector DB / LLM-runtime.
* Не создавать `.rdb` как побочный продукт (Stage 6.11 §12): пока нет реальных записей
  и `dirty=false` — файл не появляется.

## 14. Критерий завершения

Stage завершён, если:

* в схеме RDB есть разделы `protocol`, `ports`, `watchlist`; `version` поднят до 2;
* `version: 1` грузится обратно-совместимо;
* закрытые enum статусов/`scope`/`polarity` соблюдаются, неизвестное значение → ошибка;
* нельзя выставить VERIFIED*/REFUTED без method+evidence;
* append-only + supersede работают, история не переписывается;
* дедуп-фильтры `getProtocol` работают;
* mismatch sha256 не применяет `scope: rom`-записи молча;
* Controller → Agent API → MCP цепочка real (не mock), `tools/list` показывает new tools,
  `api_version` = 6;
* промоция protocol → ports/comment описана и имеет тест;
* `rdb_format.md` и `AI_AGENT_WORKFLOW.md` обновлены;
* unit/integration/regression tests проходят;
* `git diff -- src/` пуст (RDB-модификации живут в `rdb/`, `mcp/`, `agent/`);
* ничего из §13 не добавлено.

**Главный принцип Stage 6.28:**

```text
protocol  = журнал доказательств (append-only, без улики нет статуса)

JSON      = внутренний формат; API = единственный способ работы
```
