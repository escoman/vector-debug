# ТЗ — корректная загрузка ROM и эмуляция БЛК+СБР

## 1. Цель

Исправить текущую модель загрузки и Reset в debugger Vector-06C.

Требования:

1. Адрес размещения ROM определяется расширением файла.
2. После загрузки ROM процессор **никогда не должен принудительно получать PC = адресу загрузки ROM**.
3. После загрузки ROM начальное состояние CPU должно иметь `PC = 0x0000`.
4. Кнопка **Reset** должна эмулировать реальное нажатие **БЛК+СБР** на Векторе-06Ц.
5. Необходимо сохранить существующую архитектуру:

```text
GUI
  ↓
IDebugBackend
  ↓
IDebugTarget
  ↓
DebugAdapter
  ↓
Board
```

GUI не должен обращаться непосредственно к `Board`, `Memory`, CPU и другим компонентам эмулятора.

---

# 2. Определение адреса загрузки ROM

При загрузке ROM необходимо определить `loadAddress` по расширению файла.

Расширение сравнивать без учёта регистра.

Таблица:

| Расширение | Адрес загрузки |
| ---------- | -------------: |
| `.rom`     |       `0x0100` |
| `.r0m`     |       `0x0000` |
| `.r1m`     |       `0x0100` |
| `.r2m`     |       `0x0200` |
| `.r3m`     |       `0x0300` |
| `.r4m`     |       `0x0400` |
| `.r5m`     |       `0x0500` |
| `.r6m`     |       `0x0600` |
| `.r7m`     |       `0x0700` |
| `.r8m`     |       `0x0800` |
| `.r9m`     |       `0x0900` |

Для `.rNm`, где `N = 0..9`:

```text
loadAddress = N * 0x0100
```

Исключение:

```text
.rom → 0x0100
```

### Важное требование

Перед реализацией **обязательно проверить исходный `vector06sdl`**, включая историю/старую реализацию загрузки ROM, чтобы подтвердить именно эту таблицу.

Не заменять проверку предположением.

Если в исходном эмуляторе обнаружится отличающаяся логика — использовать фактическую логику `vector06sdl` и зафиксировать её в тестах.

---

# 3. Загрузка ROM

При `Load ROM`:

1. определить `loadAddress`;
2. загрузить содержимое файла в память начиная с `loadAddress`;
3. сохранить этот адрес как `romLoadAddress` в состоянии debugger-а;
4. после загрузки выполнить аппаратно-подобный старт с `PC = 0x0000`.

Принципиально запрещается делать:

```cpp
i8080_jump(loadAddress);
```

или эквивалент:

```cpp
Options.pc = loadAddress;
```

для определения начального PC загруженной программы.

### Пример

Для:

```text
game.rom
```

данные:

```text
0100: ...
0101: ...
...
```

Но после загрузки:

```text
PC = 0000
```

Для:

```text
game.r3m
```

данные:

```text
0300: ...
0301: ...
...
```

но:

```text
PC = 0000
```

---

# 4. Почему PC должен быть 0000

Загрузка программы по адресу `0x0100` не означает, что процессор начинает выполнение с `0x0100`.

После БЛК+СБР CPU стартует с:

```text
PC = 0000
```

Дальнейший переход к программе выполняется уже кодом, находящимся в памяти по адресам `0000...`.

Поэтому debugger должен позволять увидеть реальную последовательность:

```text
PC=0000
   ↓
исполнение кода 0000...
   ↓
JMP/CALL/прочий переход
   ↓
PC=0100
   ↓
программа
```

Для ROM, загруженного в другой адрес, аналогично.

Debugger не должен искусственно пропускать выполнение адресов `0000...`.

---

# 5. Исправление Reset

Текущий Reset debugger-а нельзя реализовывать только как:

```cpp
memory.detach_boot();
```

Это лишь часть эффекта БЛК+СБР.

Reset должен моделировать операцию:

```text
БЛК + СБР
```

на реальном Векторе-06Ц.

---

# 6. Семантика БЛК+СБР

При выполнении Reset:

### 6.1 Boot ROM

Начальный загрузчик должен быть отключён:

```text
boot ROM detached
```

То есть должен использоваться эффект существующего:

```cpp
ResetMode::BLKSBR
```

если он соответствует этому поведению текущего `Board`.

### 6.2 CPU

CPU должен быть сброшен в состояние аппаратного старта.

Минимально обязательное условие:

```text
PC = 0x0000
```

Не устанавливать:

```text
PC = romLoadAddress
```

### 6.3 Выполнение

После Reset CPU должен находиться в состоянии:

```text
paused
PC = 0x0000
```

Debugger не должен автоматически продолжать выполнение после Reset.

После нажатия `Run` процессор начинает выполнять код с `0x0000`.

---

# 7. Очень важный момент: Reset не должен уничтожать загруженный ROM

Если ROM уже загружен:

```text
Load ROM
    ↓
ROM находится в RAM
    ↓
Reset
    ↓
PC = 0000
    ↓
ROM остаётся в RAM
```

Reset не должен повторно загружать ROM и не должен очищать область памяти с ROM.

Иначе невозможно моделировать реальную последовательность:

```text
загрузили программу
→ БЛК+СБР
→ запуск программы
```

---

# 8. Отличие Load ROM и Reset

После реализации поведение должно быть следующим.

### Load ROM

```text
1. определить адрес по расширению
2. загрузить ROM в RAM
3. boot ROM отключить
4. CPU reset/start state
5. PC = 0000
6. debugger = Paused
```

### Reset

Если ROM уже загружен:

```text
1. эмулировать БЛК+СБР
2. boot ROM отключить
3. CPU reset
4. PC = 0000
5. RAM с загруженным ROM сохранить
6. debugger = Paused
```

Reset не должен снова устанавливать PC в адрес загрузки.

---

# 9. Не путать Reset и BLK+ВВОД

В проекте существуют два разных аппаратных действия:

```text
БЛК+ВВОД
```

и

```text
БЛК+СБР
```

Они не должны быть сведены к одному Reset.

`BLKVVOD`:

```text
boot ROM подключён
```

`BLKSBR`:

```text
boot ROM отключён
CPU начинает выполнение с PC=0000
```

Проверить фактическую реализацию `Board::ResetMode` и не менять её семантику без необходимости.

Если для корректной реализации БЛК+СБР требуется расширить `Board::reset()`, сделать минимальное изменение, не затрагивая несвязанные части эмулятора.

---

# 10. Архитектура

GUI не должен знать о расширениях ROM и не должен сам вычислять адрес.

Неправильно:

```cpp
GUI → ".r3m" → 0x0300
```

Правильно:

```text
GUI
 ↓
DebugBackend::loadRom()
 ↓
IDebugTarget::loadRom()
 ↓
DebugAdapter
 ↓
определение ROM load address
 ↓
Memory
 ↓
Board reset/start
```

Логику определения адреса желательно вынести в отдельную чистую функцию, например:

```cpp
uint16_t getRomLoadAddress(const std::string& path);
```

Она не должна зависеть от `Board`, CPU, GUI или ImGui.

# 11. Тесты

Обязательно добавить unit-тесты определения адреса.

Проверить минимум:

```text
test.rom  → 0100
test.r0m  → 0000
test.r1m  → 0100
test.r2m  → 0200
test.r3m  → 0300
test.r4m  → 0400
test.r5m  → 0500
test.r6m  → 0600
test.r7m  → 0700
test.r8m  → 0800
test.r9m  → 0900
```

Также проверить регистр:

```text
TEST.ROM
TEST.R3M
Test.R7m
```

должны давать тот же результат.

# 12. Интеграционные тесты загрузки

Создать тесты, проверяющие одновременно адрес загрузки и PC.

### `.rom`

Загрузить небольшой ROM:

```text
AA BB CC
```

Ожидать:

```text
RAM[0100] = AA
RAM[0101] = BB
RAM[0102] = CC
PC = 0000
```

### `.r3m`

Ожидать:

```text
RAM[0300] = AA
RAM[0301] = BB
RAM[0302] = CC
PC = 0000
```

Аналогично проверить `.r0m`.

---

# 13. Тест Reset

Сценарий:

```text
1. загрузить test.rom
2. убедиться, что ROM находится с 0x0100
3. установить PC в произвольное значение, например 0x1234
4. выполнить Reset
5. проверить PC == 0x0000
6. проверить, что RAM[0100...] не изменилась
7. проверить, что boot ROM отключён
8. проверить состояние debugger = Paused
```

---

# 14. Тест фактического выполнения после Reset

Создать минимальный ROM, содержащий код, позволяющий проверить прохождение через `0x0000`.

Например:

```text
0000: JMP 0100
0100: ...
```

Последовательность:

```text
Load ROM
→ PC=0000
→ Run/Step
→ PC=0100
```

Это должно доказывать, что debugger больше не пропускает старт с `0x0000`.

# 15. Не делать

Запрещается:

* устанавливать `PC = romLoadAddress` после загрузки;
* устанавливать `Options.pc = romLoadAddress` для обычного Load ROM;
* делать Reset через простое изменение GUI-состояния;
* очищать RAM при Reset;
* повторно загружать ROM при Reset;
* обращаться из GUI непосредственно к `Board`;
* добавлять GUI-зависимости в core;
* дублировать логику загрузки ROM в нескольких местах;
* менять несвязанные части `src/`;
* удалять существующие механизмы `BLKVVOD/BLKSBR/LOADROM` без необходимости.

# 17. Критерий готовности

Функция считается реализованной, если:

1. `.rom` загружается с `0x0100`;
2. `.r0m` — с `0x0000`;
3. `.r1m` — с `0x0100`;
4. `.r2m` — с `0x0200`;
5. ...
6. `.r9m` — с `0x0900`;
7. после загрузки любого ROM `PC == 0x0000`;
8. Reset оставляет ROM в RAM;
9. Reset устанавливает `PC == 0x0000`;
10. Reset отключает boot ROM;
11. после Reset debugger остаётся Paused;
12. Run начинает выполнение с `0x0000`;
13. существующие тесты не регрессировали;
14. добавлены тесты всех форматов `.rom/.r0m-.r9m`;
15. нет прямого доступа GUI к Vector core.

16. Обязательная проверка исходной логики загрузки ROM

Перед реализацией определения `loadAddress` **обязательно исследовать исходный код `vector06sdl`**, на котором основан текущий эмулятор.

Необходимо найти и проанализировать фактическую реализацию:

* определения расширения ROM;
* `rom_org` / `Options.rom_org` и связанных параметров;
* загрузки ROM в память;
* обработки расширений `.rom`;
* обработки расширений `.r0m` ... `.r9m`;
* вычисления адреса загрузки;
* места, где этот адрес передаётся в `Memory` / `Board`;
* старой логики запуска ROM после загрузки.

Особенно необходимо проверить, действительно ли используется правило:

```text
.r0m → 0x0000
.r1m → 0x0100
.r2m → 0x0200
...
.r9m → 0x0900
.rom → 0x0100
```

### Требование к результату проверки

В отчёте Qwen перед изменением кода должен явно указать:

1. в каком файле исходного `vector06sdl` находится эта логика;
2. название функции/метода;
3. фактический алгоритм вычисления адреса;
4. таблицу расширение → адрес;
5. есть ли отличия между `.rom` и `.r0m`;
6. есть ли дополнительные поддерживаемые расширения или специальные случаи.

Если фактическая логика исходного `vector06sdl` отличается от таблицы из настоящего ТЗ, **приоритет имеет исходный код**.

В этом случае:

* не реализовывать предположительную таблицу;
* сообщить обнаруженное отличие;
* адаптировать реализацию debugger-а к фактической логике исходного эмулятора;
* добавить тесты именно для подтверждённого поведения.

### Важное ограничение

Нельзя выводить адрес загрузки из имени файла каким-либо новым способом, если аналогичная логика уже существует в исходном эмуляторе.

Цель — **воспроизвести существующую семантику `vector06sdl`, а не создать новую систему форматов ROM**.

После проверки сохранить найденную логику в отдельной чистой функции debugger-а и покрыть её тестами.
