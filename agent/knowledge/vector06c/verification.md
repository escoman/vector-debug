Каждое существенное техническое утверждение проверено по одному или нескольким источникам
в порядке приоритета:

1. Исходный код эмуляторов (исполняемые модели аппаратуры).

Утверждения, подтверждённые только косвенными признаками или логическими умозаключениями,
помечены как `UNVERIFIED` или `SPECULATION` и не включены в раздел VERIFIED.

#### 4.4.2. Тайминги на Векторе (с wait states)

Видеоконтроллер добавляет wait states при обращении CPU к общей памяти (0000h–FFFFh,
включая экранную область 8000h–FFFFh).

**ВАЖНО (Peer Review):** Таблица wait states находится в **EMU80** (`Vector.cpp`,
`VectorCpuWaits::getCpuWaitStates()`), а НЕ в VSDL. VSDL использует другой механизм
тайминга — через `filler.fill(instr_time << 2)`, где CPU-такты конвертируются
в 12 МГц пиксели.

EMU80 `Vector.cpp` — таблица wait states:
```cpp
static const int waits[19] = {0, 0, 0, 0, 0, 3, 0, 1, 0, 0, 2, 5, 0, 3, 0, 0, 4, 7, 6};
// Индекс = normalClocks (не normalClocks - 1!)
```
Примеры:
- 5 тактов (MOV r,r) → wait = 3 → итого 8
- 7 тактов → wait = 1 → итого 8
- 10 тактов → wait = 2 → итого 12
- 11 тактов (RST) → wait = 5 → итого 16
- 17 тактов (CALL) → wait = 7 → итого 24
- 18 тактов (XTHL) → wait = 6 → итого 24

**VERIFIED:** Оба эмулятора дают те же результаты:
- VSDL: `v_cycles = 24` для CALL и XTHL (строки 1603, 1763)
- EMU80: `cpu_cycles + waits[n]` = 17+7=24 (CALL), 18+6=24 (XTHL)

Значения VECTOR.MD (CALL=24, XTHL=24) **полностью совпадают** с обоими эмуляторами.

| Утверждение VECTOR.MD | Такты | VSDL v_cycles | EMU80 total | Статус |
|------------------------|-------|---------------|-------------|--------|
| MOV r,r | 8 | 8 | 5+3=8 | VERIFIED |
| MVI r,d | 8 | 8 | 7+1=8 | VERIFIED |
| ADD r | 4 | 4 | 4+0=4 | VERIFIED |
| CALL | 24 | 24 | 17+7=24 | VERIFIED |
| RST n | 16 | 16 | 11+5=16 | VERIFIED |
| XTHL | 24 | 24 | 18+6=24 | VERIFIED |

**Примечание:** VSDL хранит итоговые значения `v_cycles` напрямую (уже с учётом
wait states). EMU80 хранит базовые `cpu_cycles` и добавляет wait states из
таблицы `VectorCpuWaits::getCpuWaitStates()`. Оба подхода дают одинаковый результат.

### 4.4.3. Недокументированные команды 8080

VECTOR.MD утверждает наличие недокументированных команд:

| Opcode | Документация | Статус |

## 5. Память

### 5.1. Физический объём

| Утверждение | Значение | Статус | Подтверждение |
|-------------|----------|--------|---------------|
| Основная RAM | 64 КБ | VERIFIED_BY_CODE | VSDL: `64 * 1024`, EMU80: `0x10000` |
| Экранная RAM | 32 КБ | VERIFIED_BY_CODE | 4 плоскости × 8 КБ |
| Расширенная RAM (Barkar/квазидиск) | до 256 КБ | VERIFIED_BY_CODE | VSDL: `256 * 1024` для ramdisk |

**ВАЖНО (Peer Review):** Экранная RAM (32 КБ, 8000h–FFFFh) — это **верхняя половина**
основной RAM (64 КБ, 0000h–FFFFh). Это НЕ дополнительная память. Полная карта:
- 0000h–7FFFh (32 КБ) — нижняя RAM, доступна программе
- 8000h–FFFFh (32 КБ) — верхняя RAM, используется как экранная память
- Итого: 64 КБ адресуемого RAM

TIMSOFT подтверждает: «В БПЭВМ используется общая оперативная память для микропроцессора
и контроллера графического дисплея объёмом 64 Кбайта».

### 5.2. Адресное пространство

```
0000h–7FFFh   — нижние 32 КБ (общая RAM, доступна программе)
8000h–9FFFh   — плоскость 3 (8 КБ, бит 3 цвета)
A000h–BFFFh   — плоскость 2 (8 КБ, бит 2 цвета)
C000h–DFFFh   — плоскость 1 (8 КБ, бит 1 цвета)
E000h–FFFFh   — плоскость 0 (8 КБ, бит 0 цвета)
```

**Статус:** VERIFIED_BY_CODE

**Подтверждение (VSDL):**
- `filler.cpp`: чтение плоскостей по адресам `0x8000`, `0xA000`, `0xC000`, `0xE000`
  (через `tobank()` с interleave-преобразованием).
- `memory.cpp`: `bigram_select()` определяет отображение: `0xA000–0xDFFF` → `page_map`,
  `0x8000–0x9FFF` → `page_map`, `0xE000–0xFFFF` → `page_map`.

**Подтверждение (EMU80):**
- `Vector.cpp renderLine()`: чтение 4 плоскостей по адресам `0x8000+offset`,
  `0xA000+offset`, `0xC000+offset`, `0xE000+offset`.

### 5.3. Экранная память и CPU

Процессор обращается к экранной области как к обычной RAM. Нет аппаратного разделения
или защиты экранной памяти.

**Статус:** VERIFIED_BY_CODE

**Подтверждение:** Оба эмулятора предоставляют CPU прямой доступ ко всей памяти 0000h–FFFFh
без каких-либо ограничений на экранную область.

### 5.4. Банковая организация (Barkar / квазидиск)

Порт 10h управляет банковой памятью:

| Бит | Назначение | Статус |
|-----|-----------|--------|
| 0–1 | Номер страницы map | VERIFIED_BY_CODE |
| 2–3 | Номер страницы stack | VERIFIED_BY_CODE |
| 4 | Режим stack | VERIFIED_BY_CODE |
| 5–7 | Режим map | VERIFIED_BY_CODE |

**Подтверждение (VSDL):** `memory.cpp control_write(uint8_t w8)`.

**Подтверждение (EMU80):** `VectorAddrSpace::writeByte/readByte` — Barkar и ERAM системы.

**Статус:** VERIFIED_BY_CODE

### 5.5. ERAM (расширенная RAM в EMU80)

EMU80 реализует дополнительную систему ERAM (Extended RAM) с сегментным/страничным
управлением. Это расширение эмулятора для поддержки расширенных конфигураций.

**Статус:** VERIFIED_BY_CODE (наличие в EMU80). UNVERIFIED для оригинального hardware
(ERAM может быть расширением, а не штатной функцией).

### 6.2. Boot ROM

При загрузке ПЗУ отображается в нижнюю область памяти (0000h–...). После начальной
загрузки ПЗУ отключается, и по адресу 0000h находится обычная RAM.

**Статус:** VERIFIED_BY_CODE

**Подтверждение (VSDL):** `board.cpp` — режимы `BLKSBR` (отключить boot ROM) и
`BLKVVOD` (подключить boot ROM).

### 6.3. ROM-файлы и адрес 0100h

Файлы `.rom` загружаются эмуляторами по адресу 0100h. Это наследие CP/M/MicroDOS,
где пользовательские программы формата .COM загружались с адреса 0100h.

**Статус:** VERIFIED_BY_PRIMARY_SOURCE

## 7. Видео

### 7.1. Режим 256×256

#### 7.1.1. Основные параметры

| Параметр | Значение | Статус |
|----------|----------|--------|
| Разрешение | 256×256 пикселей | VERIFIED_BY_CODE |
| Количество цветов | 16 из палитры 256 | VERIFIED_BY_CODE |
| Битовых плоскостей | 4 | VERIFIED_BY_CODE |
| Размер экранной памяти | 32 КБ | VERIFIED_BY_CODE |

#### 7.1.2. Организация байта в плоскости

Один байт плоскости содержит 8 горизонтальных пикселей:
- Бит 7 — самый левый пиксель
- Бит 0 — самый правый пиксель

**Статус:** VERIFIED_BY_CODE

**Подтверждение (VSDL):** `filler.cpp fetchPixels()`:
```cpp
(p >> 4 & 8) | (p >> 13 & 4) | (p >> 22 & 2) | (p >> 31 & 1)
```
Извлекает MSB (бит 7) каждого из 4 байтов плоскостей как биты цвета.

**Подтверждение (EMU80):** `Vector.cpp renderLine()` — аналогичное извлечение MSB.

#### 7.1.3. Адресация пикселя (256×256)

Для пикселя (X, Y), где X=0..255, Y=0..255 (Y=0 — верх экрана):

```
byte_offset = (X / 8) × 0100h + (255 - Y)
bit_number  = 7 - (X mod 8)
address     = base_plane + byte_offset
```

где `base_plane` = 8000h / A000h / C000h / E000h для плоскостей 3/2/1/0.

**Статус:** VERIFIED_BY_CODE

**Подтверждение:** Оба эмулятора используют эту формулу при формировании изображения.

#### 7.1.4. Формирование цвета пикселя

Цвет пикселя (0–15) формируется из 4 битов:

| Плоскость | Адрес | Бит в цвете | Вес |
|-----------|-------|-------------|-----|
| 0 | E000h–FFFFh | бит 0 | 1 |
| 1 | C000h–DFFFh | бит 1 | 2 |
| 2 | A000h–BFFFh | бит 2 | 4 |
| 3 | 8000h–9FFFh | бит 3 | 8 |

**Статус:** VERIFIED_BY_CODE

**Подтверждение (EMU80):** `Vector.cpp renderLine()`:
```cpp
int color = ((byte0 >> 7) & 1) | ((byte1 >> 6) & 2) | ((byte2 >> 5) & 4) | ((byte3 >> 4) & 8);
```

### 7.2. Режим 512×256

#### 7.2.1. Основные параметры

| Параметр | Значение | Статус |
|----------|----------|--------|
| Разрешение | 512×256 пикселей | VERIFIED_BY_CODE |
| Количество цветов | 4 | VERIFIED_BY_CODE |
| Размер экранной памяти | 32 КБ (все 4 плоскости) | VERIFIED_BY_CODE |
| Переключение режима | Порт 02h, бит 4 | VERIFIED_BY_CODE |

#### 7.2.2. Организация памяти

В режиме 512×256 плоскости объединяются попарно:

```
Расширенная плоскость A:
    plane 2 (A000h) + plane 3 (8000h) → для чётных X

Расширенная плоскость B:
    plane 0 (E000h) + plane 1 (C000h) → для нечётных X
```

Для каждого пикселя:
- **Чётный X** (0, 2, 4, ...): цвет из плоскостей 2 (младший бит) и 3 (старший бит)
- **Нечётный X** (1, 3, 5, ...): цвет из плоскостей 0 (младший бит) и 1 (старший бит)

**Статус:** VERIFIED_BY_CODE

**Подтверждение (VSDL):** `filler.cpp`:
```cpp
if (mode512) {
    // чередование: чётные пиксели из (index & 0x03), нечётные из (index & 0x0c)
    Palette(index & 0x03)  // плоскости 0+1, вес 1+2
    Palette(index & 0x0c)  // плоскости 2+3, вес 4+8 → сдвиг на 2
}
```

**Подтверждение (EMU80):** `Vector.cpp renderLine()` — аналогичное чередование.

**Примечание о терминологии:** В документации по Вектор-06Ц плоскости
нумеруются двумя способами:
- **Документарная нумерация:** E000h=0, C000h=1, A000h=2, 8000h=3
- **Физический порядок в памяти:** 8000h=0, A000h=1, C000h=2, E000h=3

Оба эмулятора (VSDL и EMU80) назначают плоскости **одинаково**:
- Чётный X → E000h + C000h ( documentary planes 0+1, bits 0-1)
- Нечётный X → A000h + 8000h (documentary planes 2+3, bits 2-3)

Код VSDL: `filler.cpp fill3()`: `Palette(index & 0x03)` для первого пикселя,
`Palette(index & 0x0c)` для второго. Код EMU80: `renderLine()`:
`px & 1 ? m_lastColor & 0x0c : m_lastColor & 0x03`.

#### 7.2.3. Адресация пикселя (512×256)

```
byte_group  = X / 16
byte_offset = byte_group × 0100h + (255 - Y)
bit_number  = 7 - ((X / 2) & 7)

Если X чётный:
    bit0 → A000h + byte_offset (plane 2)
    bit1 → 8000h + byte_offset (plane 3)

Если X нечётный:
    bit0 → E000h + byte_offset (plane 0)
    bit1 → C000h + byte_offset (plane 1)
```

**Статус:** VERIFIED_BY_CODE

#### 7.2.4. Веса плоскостей в режиме 512×256

| Плоскость | Для чётных X | Для нечётных X |
|-----------|-------------|----------------|
| 0 (E000h) | — | бит 0 (вес 1) |
| 1 (C000h) | — | бит 1 (вес 2) |
| 2 (A000h) | бит 0 (вес 1) | — |
| 3 (8000h) | бит 1 (вес 2) | — |

**Статус:** VERIFIED_BY_CODE

#### 7.2.5. Доступная RAM в режиме 512×256

В режиме 512×256 используются все 32 КБ экранной памяти (8000h–FFFFh).
Для программы остаются 0000h–7FFFh = 32 КБ.

**Утверждение 512x256.MD:** «512×256 с 4 цветами использует 32 КБ ОЗУ под экран» —
**VERIFIED_BY_CODE**.

**Утверждение о 512×256 с 2 цветами и 16 КБ экранной памяти:**
UNVERIFIED — требует проверки на реальном hardware. В эмуляторах такой режим
не реализован явно.

### 7.3. Палитра

#### 7.3.1. Формат ячейки палитры

Палитра содержит 16 ячеек по 8 бит. Формат физического цвета:

```
Биты:  7  6  5  4  3  2  1  0
       B1 B0 G2 G1 G0 R2 R1 R0

RRR (биты 0–2) — красный, 3 бита (0–7)
GGG (биты 3–5) — зелёный, 3 бита (0–7)
BB  (биты 6–7) — синий,  2 бита (0–3)
```

Всего 256 возможных оттенков (8 × 8 × 4).

**Статус:** VERIFIED_BY_CODE

**Подтверждение (VSDL):** `vio.h commit_palette()`:
```cpp
int b = (w8 & 0xc0) >> 6;  // биты 6-7 → синий (0-3)
int g = (w8 & 0x38) >> 3;  // биты 3-5 → зелёный (0-7)
int r = (w8 & 0x07);       // биты 0-2 → красный (0-7)
```

**Подтверждение (EMU80):** `Vector.cpp setPaletteColor()`:
```cpp
((color & 0x7) << 21)   // RRR → биты 21-23
((color & 0x38) << 13)  // GGG → биты 16-18
((color & 0xC0) << 8)   // BB → биты 14-15
```
Красный в младших битах (0-2), зелёный в средних (3-5), синий в старших (6-7).

**Подтверждение (TIMSOFT / vector_techinfo.md):**
```
D0 — 1 красный    D3 — 1 зелёный    D6 — 2 синий
D1 — 2 красный    D4 — 2 зелёный    D7 — 4 синий
D2 — 4 красный    D5 — 4 зелёный
```

#### 7.3.2. Порты палитры

| Порт | Направление | Назначение | Статус |
|------|-------------|-----------|--------|
| 02h | R/W | Порт B: биты 0-3 = бордюр, бит 4 = 512px режим, сканирование клавиатуры | VERIFIED_BY_CODE |
| 0Ch | W | Запись физического цвета в палитру | VERIFIED_BY_CODE |
| 0Dh–0Fh | W | Зеркала порта 0Ch (тоже записывают цвет) | VERIFIED_BY_CODE |

**Подтверждение (VSDL):** `vio.h`:
- `output(0x02, w8)` → `this->PB = w8` (бордюр, режим 512, НЕ индекс палитры)
- `output(0x0c..0x0f, w8)` → `this->palettebyte = w8` (сохраняет цвет)
- `commit_palette(index)` → `index` приходит из **данных пикселя** (битовые плоскости), а НЕ из PB

**Подтверждение (EMU80):** `Vector.cpp`:
- `setPortB(value)` → `setBorderColor(value & 0x0f)` + `set512pxMode(value & 0x10)`
- `VectorColorRegister::writeByte()` → `setPaletteColor(value)` — использует `m_lastColor` (из пиксельных данных)

**ВАЖНО (Peer Review):** Порт 02h (Port B) **НЕ** используется для записи номера ячейки
палитры. Порт B управляет бордюром (биты 0-3) и режимом 512px (бит 4). Номер ячейки
палитры формируется из 4-битных данных пикселя, считываемых из битовых плоскостей.

**РАЗРЕШЕНО:** TIMSoft ошибся. Порт 02h (Port B) — это бордюр (биты 0-3) и режим
512px (бит 4), а НЕ индекс палитры. Индекс палитры формируется из 4-битных
пиксельных данных, считываемых из битовых плоскостей. Эмуляторы работают корректно
с реальными ROM для Вектора.

#### 7.3.3. Механизм записи палитры

Палитра (К155РУ2) — это ОЗУ из 16 ячеек по 8 бит. **Адрес** ячейки палитры определяется
4-битным кодом цвета пикселя (из битовых плоскостей). **Данные** записываются через
порт 0Ch.

Процесс записи цвета:
1. Пиксельные данные (4 бита из плоскостей) → адрес палитры (0-15)
2. `OUT 0Ch` → записать физический цвет в ячейку палитры по текущему адресу

Палитра обновляется синхронно с развёрткой: когда луч проходит через позицию пикселя,
происходит чтение из палитры по адресу из пиксельных данных. Если в этот момент
выполняется `OUT 0Ch`, новое значение записывается в эту ячейку.

**Статус:** VERIFIED_BY_CODE (механизм подтверждён обоими эмуляторами)

#### 7.3.4. Цвет бордюра

Цвет бордюра задаётся битами 0-3 порта 02h (Port B). Это НЕ привязано к конкретной
ячейке палитры — бордюр имеет собственный 4-битный регистр.

**Статус:** VERIFIED_BY_CODE

**Подтверждение (VSDL):** `vio.h`:
```cpp
int BorderIndex() const { return this->PB & 0x0f; }
```

**Подтверждение (EMU80):** `Vector.cpp setPortB()`:
```cpp
m_borderColor = value & 0x0f;
```

**CONFLICT с VECTOR.MD:** VECTOR.MD утверждает «Цвет бордюра задаётся одним из значений
палитры (часто ячейка 15)». Это **INCORRECT** — бордюр имеет собственный регистр,
не связанный с палитрой напрямую.

#### 7.3.5. Бордюр в режиме 512×256

В режиме 512×256 бордюр использует 2 бита из 4-битного регистра:
- `borderColor & 0x03` — для одной группы пикселей
- `borderColor & 0x0c` — для другой группы

**Статус:** VERIFIED_BY_CODE

**Подтверждение (EMU80):** `Vector.cpp renderLine()` — в border area при mode512.

#### 7.3.6. Смена палитры во время кадра (racing the beam)

Палитру можно менять во время формирования кадра, что позволяет показать более 16 цветов
на одном экране.

**Статус:** VERIFIED_BY_PRIMARY_SOURCE (TIMSOFT, «Секреты Вектора»)

**Примечание:** Эмуляторы поддерживают эту возможность, но стабильность записи
зависит от конкретного экземпляра hardware.

## 15. Программирование Вектор-06Ц

### 15.1. Стандартная инициализация

```asm
        ORG  0100h
Start:  DI
        LXI  SP,StackTop
        MVI  A,0C3h         ; JMP
        STA  0000h           ; вектор сброса
        STA  0038h           ; вектор RST 7
        LXI  H,Main
        SHLD 0001h
        LXI  H,IntHandler
        SHLD 0039h
        XRA  A
        OUT  10h             ; отключить квазидиск
        EI
        JMP  Main
```

# Ошибки исходной документации

### Ошибка 1: Формат цвета палитры (VECTOR.MD)

**Старое утверждение:**
> Формат физического цвета: `Биты: 7 6 | 5 4 3 | 2 1 0` → `BB | GGG | RRR`

**Результат проверки:**
> Эмуляторы и первичная документация показывают обратный порядок.

**Правильно:**
> Формат: `RRR GGG BB` — биты 0-2 = красный, биты 3-5 = зелёный, биты 6-7 = синий.

**Доказательство:**
- VSDL `vio.h commit_palette()`: `r = w8 & 0x07`, `g = (w8 & 0x38) >> 3`, `b = (w8 & 0xc0) >> 6`
- EMU80 `Vector.cpp setPaletteColor()`: `color & 0x7` → R
- TIMSOFT `vector_techinfo.md`: `D0=1 красный, D3=1 зелёный, D6=2 синий`

**Причина ошибки:** AI перепутал порядок битов, записав старшие биты первыми.

---

### Ошибка 2: Таблица примеров палитры (VECTOR.MD §5.4.7)

**Старое утверждение:**
> `01h` = тёмно-синий, `40h` = тёмно-красный, `C0h` = ярко-красный

**Правильно (RRR GGG BB):**
> `01h` = тёмно-красный (R=1), `40h` = тёмно-синий (B=1), `C0h` = ярко-синий (B=3)

**Доказательство:** Биты 0-2 = красный. 01h = бит 0 установлен = R=1 = красный.

**Причина ошибки:** Таблица составлена в соответствии с неправильным форматом BB GGG RRR.

---

### Ошибка 3: Порт скроллинга (VECTOR.MD §5.3.6)

**Старое утверждение:**
> «Аппаратный вертикальный скроллинг управляется через порт 01h»

**Правильно:**
> Скроллинг управляется через порт **03h** (Port A ВВ55).

**Доказательство:**
- VSDL: `ScrollStart() { return this->PA; }` — PA = Port A = порт 03h
- EMU80: `setPortA()` → `m_lineOffset = value`

---

### Ошибка 4: Бордюр = ячейка палитры 15 (VECTOR.MD §5.4.4)

**Старое утверждение:**
> «Цвет бордюра задаётся одним из значений палитры (часто ячейка 15)»

**Правильно:**
> Цвет бордюра задаётся битами 0-3 порта 02h (Port B). Это отдельный 4-битный регистр,
> не связанный напрямую с ячейкой палитры.

**Доказательство:**
- VSDL: `BorderIndex() { return this->PB & 0x0f; }`
- EMU80: `m_borderColor = value & 0x0f`

---

### Ошибка 5: «3 канала + шум» в сводке (VECTOR.MD §1)

**Старое утверждение:**
> «Звук: КР580ВИ53 (3 канала + шум)»

**Правильно:**
> Звук: КР580ВИ53 — 3 тональных канала, **аппаратный шум отсутствует**.

**Доказательство:**
- 8253 — программируемый таймер, не имеет шумогенератора
- VECTOR.MD §5.5.1 сам подтверждает: «Аппаратный шумовой канал: Отсутствует»
- TIMSOFT подтверждает отсутствие шума

### Ошибка 6: Тайминги CPU без пояснения (VECTOR.MD §8) — РАЗРЕШЕНО

**Старое утверждение:**
> Таблица таймингов: MOV r,r = 8, CALL = 24, XTHL = 24

**Результат повторной проверки:**
> Значения VECTOR.MD **верны**. Предыдущий анализ ошибочно использовал wait=4
> для CALL и XTHL. Правильные значения из таблицы EMU80:
> - CALL: base=17, wait=7 → total=24 ✅
> - XTHL: base=18, wait=6 → total=24 ✅
> VSDL хранит v_cycles=24 напрямую.

**Статус:** VERIFIED — все три источника совпадают (VECTOR.MD, VSDL, EMU80).

## Errors Found During Peer Review

### Ошибка PR-1: Механизм записи палитры (разделы 7.3.2, 7.3.3)

**Текущая формулировка (была):**
> «1. OUT 02h — записать номер ячейки (0-15) в порт B (PB)
> 2. OUT 0Ch — записать физический цвет; палитра запоминает значение по индексу из PB»

**Почему неверна:**
Оба эмулятора показывают, что индекс палитры приходит из данных пикселя (битовые плоскости),
а не из порта B. VSDL: `commit_palette(index)` — `index` из `shiftOutPixels()`.
EMU80: `setPaletteColor(value)` — использует `m_lastColor` из `renderLine()`.

**Правильная формулировка:**
Палитра индексируется 4-битным кодом цвета из пиксельных данных. Порт 0Ch записывает
физический цвет в ячейку палитры по текущему индексу из пиксельного потока.
Порт B (02h) управляет бордюром и режимом 512px, но не индексом палитры.

**Источник:** VSDL `vio.h commit_palette()`, `filler.cpp shiftOutPixels()`; EMU80 `Vector.cpp renderLine()`.
**Уровень достоверности:** VERIFIED_BY_CODE (оба эмулятора согласны).

---

### Ошибка PR-2: Атрибуция таблицы wait states (разделы 4.4.2, 17.4)

**Текущая формулировка (была):**
> «VSDL board.cpp / filler.cpp — таблица wait states: {0,0,0,0,0,3,0,1,0,0,2,5,0,3,0,0,4,7,6}»

**Почему неверна:**
Поиск по коду VSDL (`vector06sdl_psp/src/`) не нашёл этого массива. Таблица находится
в EMU80: `Vector.cpp`, функция `VectorCpuWaits::getCpuWaitStates()`.
VSDL использует другой механизм: `filler.fill(instr_time << 2, ...)`.

**Правильная формулировка:**
Таблица wait states находится в EMU80 (`VectorCpuWaits`). VSDL использует пиксельный
метод тайминга через `filler.fill()`.

**Источник:** EMU80 `Vector.cpp` строка 904-908; VSDL `board.cpp single_step()`.
**Уровень достоверности:** VERIFIED_BY_CODE.

---

### Ошибка PR-3: Неясное отношение экранной RAM к общей RAM (раздел 5.1)

**Текущая формулировка (была):**
> «Основная RAM: 64 КБ» и «Экранная RAM: 32 КБ» — как отдельные строки без пояснения.

**Почему проблематична:**
Может создать впечатление, что имеется 64 КБ обычного ОЗУ + ещё 32 КБ видеопамяти.
На самом деле 32 КБ экранной памяти — это верхняя половина 64 КБ общей RAM.

**Правильная формулировка:**
Добавлено пояснение: экранная RAM (32 КБ, 8000h–FFFFh) — верхняя половина основной
RAM (64 КБ, 0000h–FFFFh). TIMSOFT подтверждает: «общая RAM 64 КБ».

**Источник:** TIMSOFT §2, VSDL `memory.h`, EMU80 `VectorAddrSpace`.
**Уровень достоверности:** VERIFIED_BY_CODE + VERIFIED_BY_PRIMARY_SOURCE.

## Независимость источников

### VSDL vs EMU80

- **Разные авторы:** VSDL — svofski; EMU80 — Viktor Pykhonin.
- **Разные архитектуры:** VSDL использует pixel-filler подход; EMU80 — объектно-ориентированную платформу.
- **Разные механизмы тайминга:** VSDL — пиксельный; EMU80 — таблица wait states.
- **Общий первичный источник:** Оба автора, вероятно, использовали TIMSoft и оригинальную документацию.

**Вывод:** Источники достаточно независимы для подтверждения фактов об аппаратуре.
Однако совпадения могут быть обусловлены общим первичным источником. Когда оба эмулятора
соглашаются в деталях, не описанных в документации (например, формат палитры), — это
сильное подтверждение.

### TIMSoft vs эмуляторы

TIMSoft — первичный источник от разработчика. Когда TIMSoft согласен с эмуляторами
(палитра, плоскости, порты) — факт надёжно подтверждён. Единственное известное
расхождение: TIMSoft ошибочно указал порт 02h как «код математического цвета»
(индекс палитры). Эмуляторы и практика показали, что порт 02h — это бордюр + режим
512px, а индекс палитры формируется из пиксельных данных. Утверждение «до 256 цветов
границы» подтверждено: technique mid-frame palette swap (`clrs.asm`).

   неизвестна: возможно 3.5 МГц, снижаемая wait states видеоподсистемы
   до ~3 МГц. Требуется осциллограф.

3. **12 утверждений остаются UNVERIFIED** — они не представлены как факты.
