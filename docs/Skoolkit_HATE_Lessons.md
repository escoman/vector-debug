# Уроки разбора H.A.T.E. и практики SkoolKit для vector-debug

> Источник: недельная сессия реверс-инжиниринга игры H.A.T.E. (Vortex Software, ZX Spectrum)
> средствами SkoolKit 10.1 с целью портирования на Вектор-06Ц (КР580ВМ80А).
> Инструменты: `sna2skool`/`skool2html`/`skool2asm`, собственный headless-трассировщик
> покрытия `coverage.py` (поверх `skoolkit.CSimulator` + `kbtracer`).
> Результат: ~4880 адресов exec-map, два базовых дизассембла (движок 9.4k строк + титры 6.5k),
> полностью расшифрованная подсистема ввода/меню/состояний.

Документ в двух частях: **I** — уроки, валидные для любого ROM-реверса на Векторе;
**II** — конкретные практики SkoolKit, которые стоит перенести в vector-debug / Agent API / MCP.

---

# Часть I. Уроки сессии HATE

## L1. Полярность портов — первое, что надо проверить

Маски клавиш в `skoolkit/kbtracer.py` **активно-низкие** (нажатая клавиша = 0-бит:
`'1': (0xF7FE, 0b11111110)`). Наш инжектор подавал их как есть (OR без инверсии).
Следствие: нажатие «1» инжектировало клавиши 2,3,4,5+CAPS. Все шесть дней прогонов
v1–v6 («игра игнорирует ввод») были испорчены багом *инструмента*, а не игры.
Фикс — одна строка: `bits ^ 0xFF`.

**Для vector-debug:**
- В knowledge base / RDB-объектах портов Вектора явно хранить **полярность и семантику
  битов** (клавиатурный порт, порты палитры 0x0C–0x0F, звук, ППО/МС). Документированная
  таблица «порт → бит → смысл, активный уровень» должна быть частью RDB, а не памяти агента.
- `debug_press_key`/`debug_type_key` должны иметь юнит-тест, проверяющий *смысл*: после
  press('X') читатель клавиатуры в ROM должен увидеть именно ожидаемый бит, а не его инверсию.

## L2. Статический анализ лжёт о «данных»; правда — только из трассировки

Ранняя разметка ctl («$D000+ — упакованная графика») была опровергнута одним наблюдением:
чекпоинт снапшота имел **PC=$E2D7, IM=2** — игра исполняла код из «графики». Итоговый
exec-map по трассе дал ~3900 RAM-адресов кода, из них десятки кластеров, которые
линейный дизассемблировщик никогда бы не нашёл сам.

**Для vector-debug:** классификация code/data в дизассембле должна seed'иться из
`debug_coverage_report` / карты выполнения, а не из эвристик по байтам. Уже есть
`debug_get_memory_access_map` + coverage — связка «exec-map → декларация кодовых записей →
детерминированная перегенерация дизассембла» — её стоит сделать *обязательным* шагом
рабочего процесса (см. P1).

## L3. Идентифицировать модуль — хешем кода, а не региона

Гипотеза «HATE — многослойные оверлеи в $8000–$CFFF» породила 2764 «уникальных оверлея»
при хешировании сырых байтов региона. Причина: $8400–$BFFF — backbuffer рельефа,
меняющийся каждый кадр. Ключевое решение: **хеш только адресов, подтверждённо исполняемых
exec-map'ом** ($CF32–$F2DF). Результат: 2 состояния вместо 2764, затем доказательство, что
движок *постоянен* (3926/3926 исполняемых адресов идентичны в титулах, аттракте и геймплее).
Гипотеза об оверлеях умерла корректно, и весь план портирования упростился.

**Для vector-debug:** при анализе банково-переключаемых ROM — хешировать/сравнивать
только исполненные адреса банковского окна; сырые сравнения снапшотов
(`debug_compare_memory_snapshots`) по всему окну дают ложную дробь. Хорошая задача для
нового MCP-инструмента: `code_fingerprint(bank_window)` → хеш по exec-map.

## L4. Чекпоинт = снапшот + именованные watch-переменные + PC

Самые полезные строчки логов за всю сессию:

```
Wrote run9_02400.z80  C28F=0 C290=01 F0DB=00 E68B=0 C000=20 PC=$D38B
```

Снимок без напечатанного состояния переменных приходится открывать и исследовать;
со снятыми значениями — эволюция состояния читается прямо из лога прогона (именно так
было найдено, что `E68B≠0` блокирует читатель ввода — «окно сообщения/автопилот»).

**Для vector-debug:** к `debug_create_memory_snapshot` добавить **watch-list**
(набор именованных адресов/диапазонов, хранящихся в workspace/RDB как объекты типа
«variable»), и печатать их значения в лог чекпоинта/на срабатывании брейкпоинта.
Это дешёвая надстройка, которая многократно ускоряет итерацию «прогон → диагноз».

## L5. Критерий остановки покрытия

Пять последних прогонов (br1–br5, ~150k эмулированных кадров) дали **0** новых адресов,
кроме 10 байт тел секретов. Это сигнал: покрытие насыщено, дальнейшие прогоны бессмысленны.
Формулировка: *N прогонов подряд с содержательным разнообразием входов (смерть, меню,
демо, пауза, секреты) дают < ε новых адресов → coverage converged*.

**Для vector-debug:** зафиксировать это как явный критерий в AI_AGENT_WORKFLOW —
агенту полезно уметь доказывать завершение фазы покрытия, а не крутить прогоны вечно.

## L6. Переменные ищутся диффом двух состояний, а не чтением листинга

Адреса счёта/флагов находились так: два снапшота в *разных* семантических состояниях
(SCORE=0 vs SCORE=420; меню vs миссия) → побайтовый diff → кандидаты с нужными
значениями. Так были локализованы $C28F (режим управления), $C290 (байт ввода),
$F0DB (флаг демо), $E68B (окно сообщений/автопилота), $C000 (флаги, вкл. bit7=DEMO).

**Для vector-debug:** у `debug_diff_memory` это уже есть («complete byte-for-byte
snapshot diff»). Практика, которой не хватает — *протокол*: состояние A ↔ состояние B
получаются скриптом (L8), diff ограничивается RAM-диапазоном, кандидаты проверяются
однократной модификацией (poke → перерисовка HUD). Стоит оформить как Task в Task Library.

## L7. Строковые таблицы — карта к семантике

Поиск печатных последовательностей в данных (ASCII и Spectrum screen-codes A=0…Z=25)
вскрыл весь UI: `' DEMO '`, `'PAUSE!'`, `'ABORT!'`, `'SELECT'`, `'1 KEYBOARD'`…
`'6 START GAME'` в $F0E4–$F1A4 — и сразу связал их с обработчиками. Секреты
(`p` = ABORT с подтверждением ENTER, `u+g` = DEMO) были найдены из кода проверки
бит клавиатуры и **подтверждены скриншотами** (окно «ABORT!», зелёный рельеф демо).

**Для vector-debug:** добавить helper (MCP-инструмент или скрипт поверх
`debug_find_bytecode_sequence`): «string scan» — найти цепочки печатных байтов ≥4 в
диапазоне, вернуть адрес+текст+кодировку (русские коды Вектора/BCD/7-bit ASCII).
Для русскоязычных ROM Вектора это вдвойне важно (таблицы перекодировки символов).

## L8. Пофреймовые скрипты ввода — базовый примитив автоматизации

Вся эмпирика собиралась скриптами вида «кадр-длительность → набор клавиш» с
директивой CHECKPOINT. SkoolKit имеет такой формат нативно (`.t2s` для `tap2sna.py`,
см. `examples/hungry_horace.t2s`) — мы фактически заново изобрели его в `coverage.py`.

**Для vector-debug:** формат + headless-раннер пофреймовых сценариев ввода
(кнопки/длительности/чекпоинты/watch-переменные) — отсутствующий примитив. Через MCP
это последовательность `debug_press_key` + шаг по кадрам, но *декларативный файл сценария*
(версия, воспроизводимость, golden-тесты) дешевле в поддержке. Идеальное место —
`workspaces/` или отдельная папка `scenarios/`, с прогоном через v06c-mcp headless.

## L9. Сначала верифицируй стенд, потом верь результатам

Баг инверсной маски (L1) шесть прогонов подряд выдавал правдоподобные, но ложные
«данные покрытия». С тех пор любая гипотеза «игра/ROM не реагирует на ввод» обязана
проверяться контрольным экспериментом на заведомо простом входе (например, ROM-тест,
который меняет палитру по клавише).

**Для vector-debug:** в CI — golden-сценарии: ROM X + сценарий Y ⇒ достижимое состояние Z
(значение переменной, кадр). Если golden не проходит — сломан инструмент, а не ROM.

## L10. Гигиена артефактов и воспроизводимость

Финальный конвейер `snapshot + ctl → skool → asm/html` — **байт-в-байт воспроизводим**
(проверено diff'ом). Ключ к этому: (а) разделять debug-осадок (чекпоинты, PNG, логи) и
деливераблы (ctl, skool, asm) — папки `tmp/ data/ asm/ html/`; (б) в шапке каждого ctl —
база-снапшот, команду генерации, найденную семантику. Свалка из 800 файлов в одной
директории стоила потерянного контекста.

# Часть II. Практики SkoolKit, полезные vector-debug

## P1. Трёхслойная архитектура: контроль → база → писатели

```
snapshot(.z80) + control(.ctl)  →  база(.skool)  →  skool2html / skool2asm / skool2bin
       (что есть что)             (разобранный     (листинги, ASM, пересборка бинаря)
                                   проект)
```

Разделение «декларация code/data» (человекоправный `.ctl`) и «дизассемблированная база»
— главный архитектурный подарок. Переконфигурировал ctl → перегенерировал всё; база
не содержит решений о классификации, только производные.

*Маппинг:* у vector-debug есть RDB (база) и экспорт ASM. Не хватает **декларативного
control-файла классификации** (код/данные/графика/текст по адресам, seed из exec-map),
хранимого в git проекта анализа и применяемого детерминированно
(`debug_analyze_code` + ctl-файл). RDB-объекты — кандидаты на роль, но ctl текстов,
ревьюабелен, диффится — этого RDB не даёт.

## P2. Типизированные записи данных

Директивы ctl: `c` код, `b` binary, `g` графика (screen-байты → PNG), `i` таблицы
инструкций, `s` строки, `t` текст с кодами экрана, `w` 16-бит слова. Каждая даёт
осмысленный вывод (например `g` рендерит карту прямо в HTML — `sna2img.py`).

*Маппинг:* для Вектора аналогично нужны режимы VI53/графики (документ VI53_MODES уже
есть), таблицы смещений (8-bit signed), строки с русскими кодами. Стоит завести
типизированные RDB-объекты данных с *рендером* (тайловая карта → PNG в output), а не
только DEFB-вывод.

## P3. Entry points + автодокументирование xrefs в комментариях

sna2skool помечает каждый адрес перехода entry-точкой (`*`), и каждая запись печатает
строку «This entry point is used by the routine at #R$CF32» — граф вызовов
**в тексте листинга**, без отдельного инструмента xrefs. Для LLM-агента это
резко повышает плотность полезного контекста на строку дампа.

*Маппинг:* экспортёр ASM/листингов vector-debug должен печатать xref-заголовок для
каждой функции (данные уже есть: `debug_get_xrefs`, call graph).

## P4. Макросы комментариев: один источник знания, разная рендеринга

Комментарии в базе хранятся с макросами `#R<адрес>` (ссылка на рутину), `#N<значение>`,
`#REGa` (регистр), `#B<бит>`. Один и тот же комментарий рендерится: в ASM — `LCF32_6`
(метки), в HTML — `<a href>` (гиперссылка), в decimal-режиме — десятичные числа.
Знание не дублируется между выходами.

*Маппинг:* комментарии RDB-объектов сейчас — строки навсегда. Параметризованные ссылки
(`@func:0x1234`, `@var:0x2000`) с рендерингом в текущую нотацию — сильное улучшение
для переноса/рефакторинга адресов (сдвиг ROM → ссылки живут, текст нет).

## P5. Instruction utility: автокомментарии семантики инструкций

SkoolKit генерирует комментарии *для каждой инструкции*: `LD A,($F0DB)` →
«A=PEEK $F0DB», `JR Z,X` → «Jump to X if A=0», `IN A,($FE)` с маской строки →
«Read keys Q-W-E-R-T», `BIT 3,A` → «Set the zero flag if bit 3 of A is 0».
Человек (и агент) читает листинг как псевдокод. Именно подсказки «Read keys …»
направили нас к расшифровке всего ввода.

*Маппинг:* для 8080 — таблица автокомментариев по (opcode, операнд):
`IN 0x??` → семантика порта из таблицы L1; `OUT (C)` → «палитра: биты 0–2 = …»;
`CALL`/`RST` → имя функции. Это самый дешёвый путь к self-explanatory листингу для
агента. Вероятно, частично есть в дизассемблере — стоит проверить плотность и
дополнить до «предложение-уровня» комментариев.

## P6. `.ref` — внешняя база знаний, не входящая в базу разбора

Файл `.ref` даёт метки, описания и комментарии по адресам из внешнего источника,
сливаемого на этапе вывода. Знание о ROM живёт отдельно и догружается постепенно,
без переразбора.

*Маппинг:* RDB ближе всего, но idea «merge-time injection» полезна: общий
(не-ROM'ный) слой знаний — системные вызовы Вектора/ROM-монитор, порты — один на все
проекты; проектный слой — в workspace. Не смешивать.

## P7. Round-trip верификация: skool2bin

Дизассембли → пересборка → побайтовое сравнение с оригиналом. Это одновременно
доказательство корректности разбора и тест дизассемблера/экспортёра.

*Маппинг:* у vector-debug уже есть известные баги класса ASM exporter
(NOP opcodes, `Known_Issue_ASM_Exporter_NOP_Opcodes.md`). Round-trip тест
(ROM → полный анализ → экспорт ASM → ассемблирование → diff) ловит такие баги
автоматически и даёт метрику «разобрано и пересобрано N% ROM» — честнее, чем
процент покрытия строк.

## P8. Директивы @label/@bytes/@if/@*sub/@*fix — ремасштабируемость вывода

`@ofix/@ssub/@rsub` управляют тем, что подставляется в ASM (метки/числа/фиксы),
`@start/@end` — секционированием вывода. Урок для нас был суров: skool2asm по умолчанию
печатает только между @start/@end → «пустой» вывод без ошибки.

*Маппинг:* при проектировании режимов экспорта vector-debug — **никогда не молчать**:
пустой вывод при непустом входе = предупреждение/ошибка (у нас вывел «Parsed… Wrote ASM»
и 0 строк; обманчивый успех).

## P9. Система предупреждений о перекрытиях

sna2skool предупреждает о пересечении записей (1-byte overlaps на границах кластеров).
Дешёвая, но отловившая несколько реальных ошибок класса «записи пересекаются / адрес
помечен и кодом и данными».

*Маппинг:* валидатор RDB: пересечения объектов, данные-помеченные-как-код внутри
exec-map и наоборот — отчёт по запросу, а не молчаливое состояние.

## P10. Эталонный пример-проект в репозитории

`examples/hungry_horace.{ctl,ref,t2s}` — полный рабочий пример методологии:
загрузка с ленты → снапшот → ctl+ref → HTML-книга. И человек, и LLM-агент
учатся по нему быстрее, чем по справочнику.

*Маппинг:* у vector-debug есть интеграционные тесты с реальными ROM
(putup.rom, TESTAY.ROM, FIRE3) — отличная основа; не хватает **эталонного результата
анализа** (ожидаемый RDB/отчёт покрытия/ключевые функции) рядом с каждой ROM, т.е.
golden-файлов анализа. Тогда «агент разобрал ROM» проверяется сравнением с эталоном.

## P11. Capability marker и версионирование формата

SkoolKit версионирует формат skool-файла; vector-debug уже делает похоже
(`v06c.api_version` в initialize, 2..5) — практика правильная, продолжать:
каждый новый класс инструментов (raster, batch) — +1 к версии, клиенты не гадают.

# Что НЕ стоит заимствовать

- **Python-симулятор как основной трассировщик** (`simulator.py` медленный; сам SkoolKit
  при наличии C-симулятора (`c/csimulator.c`) использует его — наш coverage.py на
  CSimulator делал ~440M операций за минуты). Архитектура vector-debug (C++ backend)
  уже правильная.
- **Jinja-подобные HTML-шаблоны** SkoolKit — избыточны; достаточно фиксированного
  листинг-рендерера.
- **Z80-специфика ctl**: записи предполагают фиксированные длины инструкций — на 8080
  это тоже верно, но банкинг Вектора требует явного указания страницы в ctl
  (аналог `bank=` в SkoolKit есть — стоит посмотреть в его сторону).

# Приоритетная пятёрка (если брать только пять пунктов)

1. **P5** — автокомментарии семантики инструкций 8080 + таблица портов Вектора с
   полярностью (L1) — мультипликатор качества работы LLM-агента над листингом.
2. **P1+L2** — декларативный control-файл классификации code/data, seed из exec-map,
   детерминированная перегенерация дизассембла.
3. **P7** — round-trip верификация (экспорт ASM → сборка → diff) как CI-тест и метрика.
4. **L4+L8** — watch-list переменных в чекпоинтах + пофреймовые сценарии ввода
   (декларативный файл, golden-сценарии в тестах).
5. **L3** — fingerprint-инструмент для банково-переключаемого кода (хеш по исполненным
   адресам окна).
